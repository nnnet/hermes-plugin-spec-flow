## Context

Замер ⏱ на живом p4 показал, куда уходит время: **ревью спеки ~47%**,
жизненный цикл 19%, интеграция 15%, починка 14%, генерация LLM ≈0%. То есть
узкое место — ревью и реворк, не троттлинг и не сама генерация.

Движок сегодня: роль = один вызов модели. Оркестр (команда разнородных
агентов) и декларативный воркфлоу **не существуют** — `run_cases.py` читает из
кейса ровно 15 ключей, среди них нет `orchestra/team/workflow/executor`. Любой
такой блок в YAML сейчас = **мёртвый конфиг**. Поэтому строим строго по слоям:
сначала движок учится читать блок, потом блок появляется в p6, потом перепрогон
и сравнение.

`p6_micro_notes` — это **линейка** (ruler): крошечный 2-эндпойнтный сервис,
полный конвейер за минимум времени, ничего не засеяно (`acceptance:` —
декларативный оракул). Каждый рычаг меряется «до/после» на p6 через
`compare_runs.py` и ⏱-вкладку.

**Жёсткие правила (соблюдать на каждом шаге):**
- Тесты p6 — только **free OpenRouter** (+ haiku/подписка как фолбэк), платные
  НИКОГДА.
- **Никакого scaffolding**: рычаги — это общая способность движка (тиринг ревью,
  механические гейты, оркестр), включаемая флагом в конфиге. p6 включает флаг —
  это измерение улучшения движка, НЕ подсказка тесту. Засев кода/ответов в p6
  запрещён.
- **Никакого мёртвого конфига**: блок в `workers:`/`review:`/`integrate:` p6
  добавляется ТОЛЬКО в том шаге, где движок начал его читать. Дефолт каждого
  флага = выкл → существующие кейсы (p4/p5) не меняются.
- Каждый шаг = тесты зелёные + commit + push + перепрогон p6 + `compare_runs`.
  Регрессия качества (ложный PASS, упавший first_pass_rate) ветирует выигрыш
  скорости.
- Навигация — Serena; пути — от корня репо; ветка `feat/roadmap-phase-1`.

## Модель HITL-инъекции (решено 2026-06-14)

Человек в HITL даёт **только требование словами** (`statement` → REQUIREMENT.md) и
**возможные ответы** (`answers`), которые выдаются плагину **только когда воркер
спросит** и **только на заданный вопрос** (диспетчер матчит вопрос по `faq.match`,
иначе `default`; проактивно — никогда). **Тест человек НЕ пишет** — это и
нереалистично, и scaffolding.

Приёмку инъекции **создаёт система сама**: сегодня воркер по TDD пишет лист + свой
тест (риск самооценки); независимую приёмку из прозаического требования генерит
**тестер-агент D1** / **специалист-ревьюер C2** — это рычаг движка, не поле YAML.
Никаких `acceptance_test:`/`from:`-папок в сценарии (удалены). Базлайны v001/v002
(зеленели с подкинутым защищённым тестом) — устарели; нужен свежий baseline на
prose-only инъекции.

## Шаг D1 — Оркестр реализатора (команда вместо одного агента)

**Цель:** на лист — мини-команда разнородных агентов: **архитектор** (задаёт
интерфейс модуля) → **кодер** (пишет; сегодняшний ансамбль креаторов) →
**тестер** (пишет+гоняет тесты) → **ремонтник** (diff-починка). Сегодня кодер и
ремонтник уже встроены в `_implement_chat`; D1 выносит шаги в явную
конфигурируемую цепочку и добавляет архитектора и тестера.

**Где:** `role_worker.py:make_implementer` — вместо монолитного `_implement_chat`
ввести `_orchestra_run(ctx, team)`: последовательность шагов по декларации; шаг
без декларации = сегодняшний единственный агент.

**Конфиг (минимальная схема D3):** `workers.implementer.team:` — список шагов
`[{role, skill, model?}]` + простые передачи (выход архитектора → вход кодера и
т.д.). **Дефолт: блока нет → команда-из-одного = текущий путь** (p4/p5 без
изменений). Читать через `configure_workers`/`WORKERS_CFG`.

**p6:** добавить блок `team:` в `workers.implementer` ТОЛЬКО после того как
движок его читает; перепрогон; сравнить `first_pass_rate`, `errors_per_node`,
`calls_per_node` (оркестр дороже по вызовам — смотрим, окупается ли качеством).

**Тесты:** юнит на `_orchestra_run` (team-of-one ≡ старое поведение; 4-шаговая
команда вызывает архитектора→кодера→тестера→ремонтника по порядку, с передачами).

## Шаг A1 — Тиринг ревью (простой узел → лёгкая проверка)

**Цель:** простой узел проходит ТОЛЬКО детерминированную проверку (spec-lint +
контракт/импорт-детекторы), без вызова LLM-ревьюера и без цикла реворка; чисто ⇒
авто-PASS. Сложный узел → полный LLM-ревью + реворк (как сейчас).

**Где:** `spec_flow_runner.py:_review_gate` — перед `_consult_reviewer` (~1546)
вставить гейт сложности на `node["metrics"]`.
- **Простой** = атомарный лист, `open_decisions==0`, `estimated_loc` мал (≈<60),
  нет детей, на/глубже `leaf_depth`. → `_lint_spec_traceability`, чисто ⇒ PASS,
  пропустить ревьюера и реворк.
- **Сложный** = ветка (есть дети) ИЛИ есть open_decisions ИЛИ большой LOC ИЛИ
  малая глубина (архитектурный узел). → полный путь.

**Конфиг:** `review.tiering: true` + `review.simple_max_loc: 60`. Дефолт выкл.

**p6:** включить; перепрогон; цель — review-ops −2–3×, `first_pass_rate` НЕ
падает (нет ложных PASS — это ветирует).

**Тесты:** классификатор simple/complex по метрикам; простой узел не дёргает
ревьюера-заглушку, сложный дёргает.

## Шаг B1 — Pre-integrate контракт-гейт (механические проверки до pytest)

**Цель:** дешёвые AST/regex/subprocess-проверки ДО дорогого integrate — fail
fast, дешевле починка.

**Где:** `pytest_verifier.py:verify` — перед `run_suite` (564) вызвать
`_pre_integrate_checks(root, targets)`. Сегодня детекторы бегут только ПОСЛЕ
красного прогона — переиспользовать их как пре-гейт + добавить из каталога.

**Каталог (без вызова модели):**
- [x] есть (после красного): export-contract (`_cross_module_import_violations`),
  dup-owner (`_duplicate_table_owners`), non-ASCII/syntax (`_non_ascii_offenders`),
  AC↔REQ (`_lint_spec_traceability`).
- [ ] новые: **арность/сигнатура вызова** (`f(a,b)` vs `def f` по модулям, AST);
  **контракт маршрутов** (каждый эндпойнт зарегистрирован ровно раз, method+path);
  **колонки БД** (insert/select колонок ⊆ define_table/CREATE);
  **форма payload** (хендлер строит ключи из контракта, эвр. AST/строки);
  **неопределённые имена** (pyflakes-style, переиспользовать `_module_exports`);
  **собираемость тестов** (`pytest --collect-only`, без прогона).
- Правило: LLM нужен только для СЕМАНТИКИ; всё выразимое статикой/без-прогона —
  механическое и НЕ тратит вызов модели.

**Где живёт:** новый модуль `tests/harness/contract_checks.py` (AST-хелперы рядом
с паттерном `_module_exports`); `verify` зовёт его пре-гейтом, FAIL → в починку
без полного pytest.

**Конфиг:** `integrate.pre_gate: true`. Дефолт выкл.

**p6:** включить; перепрогон; цель — `errors_per_node`/стоимость починки вниз,
integrate `first_pass_rate` вверх.

**Тесты:** на каждую новую проверку — позитив/негатив на синтетических src/.

## Шаг C1 — Ростер исполнителей + маршрутизация задача→исполнитель

**Цель:** исполнитель листа выбирается по ДОМЕНУ узла: специалист-агент
(db/web/api/python) ИЛИ целая команда (D1) — не сменой модели (это была тонкая
версия П13 «роль×модель»).

**Где:** `spec_flow_runner.py:_resolve_specialty` уже выводит домен; расширить с
«роль×модель» до «роль×исполнитель», где исполнитель = профиль агента или
team-спека из D1. `specialty.resolve_specialty` — точка вывода домена.

**Конфиг:** `workers.executors:` — карта домен→исполнитель (агент или команда).
На каждый лист: вывести домен, диспатчить совпавшего исполнителя; дефолт = общий
(текущий).

**p6:** web_ui-лист → web-исполнитель; сравнить именно на этом узле.

**Тесты:** маршрутизация домена к исполнителю; неизвестный домен → дефолт.

## Шаг D2 — Оркестр декомпозера

Драфтер рисует дерево → критик улучшает → согласователь сводит. Плохое дерево —
самая дорогая ошибка вниз по потоку. Тот же механизм команды, что D1, но на роли
decomposer.

## D3 — Декларативная команда + воркфлоу (схема)

Поставляется инкрементально: минимум в D1 (`team: [шаги]` + передачи), обобщается
до ростер + взаимодействие (порядок, передачи, branch/loop/parallel, что каждый
видит от других) как движок за C и D. Дефолт = команда-из-одного, один шаг =
сегодняшний единственный агент.
