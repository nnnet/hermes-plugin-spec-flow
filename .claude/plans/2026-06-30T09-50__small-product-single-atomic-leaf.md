# #122 — крошечный продукт собирать одним атомарным листом

## Что доказал прогон v125 (улики, не догадки)
- Декомпозер (claude/sonnet) раскрошил микро-«notes» на 8 листьев, среди них
  ТРИ конкурирующих «целых приложения»: `app.py` (`wsgi_app`), `wsgi_app.py`
  (`wsgi_app`), `_product_logic.py` (`application`) + отдельный `db_layer.py`.
- Хендлеры в `wsgi_app.py` корректны и делят хранилище через `db_layer` (sqlite),
  привязка их и берёт. Значит RED НЕ от конфликта привязки.
- Корень — **хрупкая загрузка собранной точки входа**: `app.py` делает
  `from _product_logic import *` + `from ping_text import get_ping` + sqlite-схема
  не инициализирована до первого запроса. Если точка входа падает на импорте/
  первом запросе — не служит НИ один маршрут (и smoke `/health`, и e2e `/notes`).
- Чем больше модулей (8 вместо 1), тем больше шансов сломать импорт/композицию.
  Доктор не сходится (resolved_ratio 0.11): дефект структурный, по-листно не лечится.
- Цена: 343 вызова / ~35 мин на сервис из ~5 файлов.

## Решение (лечит и корректность, и время)
Продукт с МАЛЫМ числом объявленных маршрутов собирать **одним атомарным листом**:
один модуль = все хендлеры + хранилище. Точку входа движок синтезирует сам (Фаза 1).
Итог: общий стейт (roundtrip честно зелёный), нет конкурирующих приложений, один
импорт-поверхность, ~6 вызовов вместо 343. Порог по числу маршрутов защищает
p4/p5 (они крупнее — продолжают дробиться).

## Где править
- `spec_flow_runner.py::_visit`, перед гейтом лист/ветка (строки ~5303-5317):
  для КОРНЕВОГО product-узла (`parent is None`, depth корня) при
  `len(self._declared_route_set(self._product_contract() or {})) <= SMALL_PRODUCT_ROUTES`
  (порог ~5) и `open_decisions==0` — выставить `node["atomic"]=True` ДО `leaf_check`
  (→ `atomic_claim=True` → leaf). Emit milestone «small product → single atomic
  leaf (N routes <= порог): one module owns all routes, engine synthesizes entry».
- Новый порог-дефолт `SMALL_PRODUCT_ROUTES` (cfg-перекрываемо через `workers`),
  по умолчанию ~5. JSON-serializable, тест на `json.dumps` если кладётся в node/meta.
- Проверить, что одиночный лист проходит Фазу 2 (`_leaf_handler_gate`): один модуль,
  определяющий post_notes/get_notes/get_health/get_ui — гейт довольный.
- Путь поздних просьб: с одним продукт-листом surface-детектор заводит late-req в
  тот же единственный модуль — проверить, что не плодит второй модуль.

## Проверка
1. Офлайн: новый тест — движок с малым контрактом (≤ порог) классифицирует
   корень как leaf; с большим (> порог) — branch (p4/p5 не задеты). Плюс весь
   `pytest tests/coverage tests/harness` зелёный.
2. Отвязанный живой прогон p6 (`tests/run-detached.sh --case p6_micro_notes
   --depth product --workers real --doctor-enabled`): ждём ОДИН продукт-модуль,
   честное READY, все маршруты служат (/health, POST/GET /notes, /ui, поздние),
   wall заметно ниже 35 мин, вызовов в разы меньше 343.
3. Регресс p4/p5 (по одному отвязанному прогону): дробление сохранилось, не хуже.

## Что НЕ делать
- НЕ патчить эвристику `_plan_ownership_report` (диагностика по упоминанию пути).
- НЕ угадывать в резольвере «какой из двух хендлеров настоящий» — корень в
  пере-дроблении, а не в привязке.
- Порог не задирать так, чтобы p4/p5 схлопывались в один лист.
