# spec-flow — план развития: e2e → качество агентов → пилот → Гермес

Дата: 2026-06-11. Продолжение `2026-06-11T00-00__roadmap-and-architecture-decisions.md`
(Фазы 1–8 закрыты, 311 тестов зелёные, ветка `feat/roadmap-phase-1`).

Порядок выбран по принципу «сначала измерить, потом чинить, потом доказать,
потом возить в транспорт»: 1 → 4 → 2 → 3. Пункты 5 и 6 — опциональные, в конце.

Правила исполнения:
- живые прогоны (LLM) — только с согласия пользователя, модель по умолчанию haiku
  (`SPEC_FLOW_LLM_MODEL`);
- каждый прогон — в свой воркспейс `tests/runs-out/<метка>__<кейс>/`,
  все артефакты и отчёты внутри;
- все отчёты строит код плагина (`build_run_report`, `build_oracle_report`),
  не человек и не агент;
- после каждого шага: полный прогон тестов, отметка чекбокса, коммит с трейлером
  `Co-Authored-By`, пуш.

## Этап 1 — полные e2e прогоны без Гермеса + анализ

Цель: первая реальная оценка ценности. До сих пор живьём прогнан один лист
(kvstore). Теперь — все кейсы, живые decomposer + implementer.

- [x] 1.1 Скрипт `tests/live_e2e_run.py`: один кейс за вызов; живой decomposer
      (дерево строит плагин сам, `tree` кейса — только оракул) + живой
      implementer (`--implementer llm`); флаги `--case`, `--depth`, `--model`;
      артефакты и отчёты — в воркспейс прогона. `run_cases._run_full`
      параметризован (implementer auto/llm, счётчик, model). Плумбинг проверен
      офлайн `tests/test_live_e2e_harness.py` (5).
- [x] 1.2 Учёт стоимости: `tests/harness/cost.py` (`Meter`, `write_cost_md`) —
      число вызовов LLM по ролям + токены (если бэкенд отдаёт) в `COST.md`/`.json`
      воркспейса; лимит вызовов на прогон (`max_decompose_calls`).
- [ ] 1.3 Прогон p1 (самый простой) на глубине execute. Анализ: глубина и форма
      дерева против оракула, качество кода листьев, зелёность тестов.
- [ ] 1.4 Прогон p2 и p3 на глубине execute. Анализ отклонений: где decomposer
      мельчит/укрупняет, где implementer пишет заглушки вместо логики.
- [ ] 1.5 Прогон p4 (полный кейс) на глубине product: policy block→pass, обе
      ревизии, HITL, приёмка. Честный вердикт PRODUCT-RESULTS (ожидаемо
      NOT READY или лучше).
- [ ] 1.6 Сводный анализ `docs/e2e-analysis.md`: таблица по кейсам — оракул
      ок/нет, покрытие скиллов/профилей, аудит R1–R9, стоимость, главные
      слабости агентов (вход для этапа 4). Сам файл — выжимка из
      плагин-отчётов, не пересказ.

## Этап 4 — качество агентов (по итогам этапа 1)

Цель: починить слабое, измеримо. Мерило «до/после» — те же e2e прогоны.

- [ ] 4.1 Разбор слабостей из 1.6: список конкретных дефектов промптов
      (decomposer: размер/метрики/глубина; implementer: заглушки, нечестные
      тесты, несоответствие спеке).
- [ ] 4.2 Итерация промпта decomposer: жёсткие правила размера листа, запрет
      пустых веток, привязка метрик к реальности; A/B на p1 — то же дерево
      стабильнее (3 прогона, оракул зелёный 3/3).
- [ ] 4.3 Итерация промпта implementer: запрет заглушек, требование настоящих
      ассертов, самопроверка перед ответом; мерило — листья p2 зелёные и
      содержательные.
- [ ] 4.4 Модели по ролям: decomposer на haiku, implementer на haiku vs sonnet —
      сравнить качество/стоимость на одном кейсе; зафиксировать выбор в
      `docs/e2e-analysis.md`.
- [ ] 4.5 Судья-оценщик (опция этапа): агент-рецензент сравнивает код листа со
      спекой и выносит вердикт; включается флагом, в тестах — стаб.
- [ ] 4.6 Повторный e2e (как 1.3–1.5) после правок: таблица «до/после» в
      `docs/e2e-analysis.md`.

## Этап 2 — пилотный продукт (доказательство ценности)

Цель: не сценарий, а реальная цель — плагин строит работающий продукт.

- [ ] 2.1 Выбрать цель пилота с пользователем: маленькая, проверяемая, полезная
      (например CLI-утилита или маленький HTTP-сервис); записать цель,
      constitution и приёмку в `tests/scenarios/pilot_*.yaml` (без `tree` —
      только оракул-границы и приёмка).
- [ ] 2.2 Прогон на глубине product с живыми агентами (модель — по выбору из
      4.4); HITL включён — пользователь подтверждает спеку и спорные узлы.
- [ ] 2.3 Приёмка по-настоящему: entrypoint в acceptance, smoke/e2e реально
      выполняются, PRODUCT-RESULTS READY/NOT READY честно.
- [ ] 2.4 Если NOT READY — цикл самосовершенствования вживую: сигнал приёмки →
      ревизия → re-derive → повторная приёмка (бюджет итераций ограничен).
- [ ] 2.5 Итог пилота в `docs/pilot-results.md` (из плагин-отчётов): что
      построено, сколько стоило, сколько итераций, где потребовался человек.

## Этап 3 — интеграция с Гермесом (только транспорт)

Цель: подключить готовую логику к боевому исполнению. Вся логика уже
оттестирована офлайн (Фаза 8) — стыкуется транспорт.

- [ ] 3.1 Живой kanban: `specflow_init`/`speckit_import`/план доски Ф8.1
      проигрываются на настоящем `hermes kanban`; проверить `--parent`-связи и
      статусы на реальной доске.
- [ ] 3.2 Диспетчер шлюза вместо офлайн-`dispatch`: воркер-процесс на карточку,
      те же волны; сверка с офлайн-волнами на одном кейсе (паритет порядка).
- [ ] 3.3 Durable-состояние: журнал/снапшоты Ф8.3 переезжают в Kanban runs
      (хранилище меняется, семантика — нет); рестарт воркера на живой доске.
- [ ] 3.4 HITL-канал: вопросы approver доставляются человеку через шлюз
      (уведомление + ответ), таймаут → безопасный отказ.
- [ ] 3.5 Интеграционный smoke-тест на стенде с Гермесом: p1 на глубине
      execute через доску end-to-end; результат и отчёты совпадают с офлайн.
- [ ] 3.6 Обновить README (раздел Run) и `docs/evaluation-guide.md` под боевой
      режим.
