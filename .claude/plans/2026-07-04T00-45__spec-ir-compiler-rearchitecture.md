# Переосмысление spec-flow: спека-IR как единственный источник, движок-компилятор

Дата: 2026-07-04. Контекст: v149–v164 — 16 прогонов, ~30 правил аудита,
v163 работал целиком, v164 снова сломан. Диагноз подтверждён юзером:
цель — УНИВЕРСАЛЬНЫЙ софт (каждый раз новые задачи, без памяти прошлых
проектов), спеки — единственный источник правды, независимость от
мощности модели. Кэш/инкрементальность отвергнуты как костыль-память.

## Корневая ошибка текущей архитектуры

ЛЛМ размазана по всем стадиям, стадии общаются ПРОЗОЙ. Каждая пара
прозаических артефактов — место дрейфа. Все правила S10.9–S12.16 — один
класс: «два артефакта разошлись в значении, не существовавшем как
данные». Аудит ловил рассогласования постфактум вместо их устранения
по построению.

## Целевая форма

Единый машинный IR (структурированная спека): узлы графа + ПОЛНЫЙ
замкнутый интерфейс каждого узла (маршруты: метод/путь/статус/media/
форма запроса/форма ответа; символы с сигнатурами; конфигурация/env).
Всё, чего нет в интерфейсе, — запрещено (закрытый мир). Из IR
детерминированно КОМПИЛИРУЮТСЯ: читаемые спеки, привязки, каркасы
модулей, тесты соответствия, точка входа, директивы лечения.

ЛЛМ ровно в двух местах:
1. описание → IR (схемная валидация + существующие план-гейты);
2. тела функций в движковом каркасе (каркас неприкосновенен — дверь).

## Пять перестроек (из существующих кирпичей)

1. IR-схема: слить interface.json + modules.json + request_fields +
   media + env (~70% уже есть) в одну замкнутую схему на узел; ворота
   проверяют конформность целиком, не аспекты по одному.
2. Тесты соответствия генерирует движок из IR — ЛЛМ-тестер на уровне
   интерфейса исчезает (класс «тестер угадал» устраняется по построению;
   за ЛЛМ — только доменные краевые случаи сверх интерфейса, опционально).
3. Каркас модуля пишет движок (сигнатуры, таблица маршрутов, список
   разрешённых импортов); модель заполняет только тела функций; дверь
   запрещает править каркас.
4. Лечение = переспрос ОДНОЙ функции с контрпримером (вход/ожидалось/
   получилось); полная перепись файла — никогда. Модель-независимость
   через минимизацию степеней свободы + бинарную обратную связь.
5. Универсальность = батарея случайных маленьких спек разных доменов
   (генератор задач), конвейер обязан собрать все, без памяти между ними.
   p6 перестаёт быть единственным мерилом.

## Порядок работ

Фаза A: IR-схема + слияние существующих данных + валидатор (замкнутый мир).
Фаза B: генератор тестов соответствия из IR (снимает тестера с интерфейса).
Фаза C: синтез каркасов из IR + дверь на каркас + тела-функции как
  единственная зона ЛЛМ.
Фаза D: лечение переспросом функции с контрпримером.
Фаза E: декомпозер выдаёт IR (не прозу) со схемной валидацией.
Фаза F: батарея случайных спек как основной прогон универсальности.
Каждая фаза — по храповику: красные правила аудита до кода.

## Дополнение (2026-07-04, разбор текста про BDD/harness от юзера)

Признание: стандарт обсуждался ещё после v150 (Gherkin/GS1), но G-W-T
остался прозой в карточках — исполняемого раннера сценариев я не построил.
Это и есть корень «одноразовых вайб-планов» и разросшегося аудита.

Уточнения к фазам:
- Фаза A: IR несёт СЦЕНАРИИ первым классом. Формат — не полный Gherkin
  (парсер станет источником проблем), а крошечная замкнутая схема,
  которой владеет движок: Given (состояние/env) — When (метод, путь,
  тело) — Then (статус, media, сверка тела). Сценарии группируются по
  требованиям (папка = требование).
- Фаза B: раннер сценариев = единственный оракул интерфейса, парсит на
  лету, гоняет как e2e через WSGI-поверхность (чёрный ящик). ЛЛМ-тесты
  интерфейса отменяются полностью. Нарушение сценария = красная сборка.
- Поздние инъекции: требование → файл сценария (красный) → реализация →
  зелёный (TDD-петля продукта).
- HITL: человек согласует поведение на уровне читаемых сценариев.
- Референсы: OpenAI harness engineering (доки актуальны, harness
  верифицирует), BDD/Cucumber-модель (иерархия требования → сценарии →
  исполняющий раннер), event-driven specs — на вырост для 10k+ сценариев.
