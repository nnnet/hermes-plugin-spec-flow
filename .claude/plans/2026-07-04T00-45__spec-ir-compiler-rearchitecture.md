# Переосмысление spec-flow: спека-IR как единственный источник, движок-компилятор

Дата: 2026-07-04. Контекст: v149–v164 — 16 прогонов, ~30 правил аудита,
v163 работал целиком, v164 снова сломан. Диагноз подтверждён юзером:
цель — УНИВЕРСАЛЬНЫЙ софт (каждый раз новые задачи, без памяти прошлых
проектов), спеки — единственный источник правды, независимость от
мощности модели. Кэш/инкрементальность отвергнуты как костыль-память.

## Корневая ошибка текущей архитектуры

ЛЛМ размазана по всем стадиям, стадии общаются ПРОЗОЙ. Каждая пара
прозаических артефактов — место дрейфа. Все правила S10.9–S12.16 — один
класс: «два артефакта разошлись в значении, не существовавшем как
данные». Аудит ловил рассогласования постфактум вместо их устранения
по построению. Урок v164: часть «прачечной» жила в детерминированном
коде самого движка (роутер-шаблон) — ревизия движковых шаблонов обязательна.

## Целевая форма

Единый машинный IR (структурированная спека): узлы графа + ПОЛНЫЙ
замкнутый интерфейс каждого узла (маршруты: метод/путь/статус/media/
форма запроса/форма ответа; символы с сигнатурами; конфигурация/env;
сценарии Given/When/Then первым классом). Всё, чего нет в интерфейсе, —
запрещено (закрытый мир). Из IR детерминированно КОМПИЛИРУЮТСЯ:
читаемые спеки, привязки, каркасы модулей, тесты соответствия, точка
входа, директивы лечения.

ЛЛМ ровно в двух местах:
1. описание → IR (схемная валидация + существующие план-гейты);
2. тела функций в движковом каркасе (каркас неприкосновенен — дверь).

## Граф работ

Каждый узел — по храповику: красные правила аудита ДО кода, красный И
зелёный кейс на каждый гейт. Исполнение: на каждом шаге искать узлы без
незакрытых зависимостей и вести их ПАРАЛЛЕЛЬНО (несколько исполнителей —
каждый в своём worktree); последовательно — только когда узлы толкаются
в одних файлах.

Топология и статусы (источник правды; секции ниже — содержание):

или осознанный worktree+merge с записанным порядком влития. Сейчас
пересечение на spec_flow_runner.py: B1∥E1 идут worktree'ами (правки
в разных функциях: верификация vs приём декомпозиции), порядок влития
B1 → E1; C1 отложен до влития B1 — его зона (синтез каркасов) граничит
с раннерными правками B1, а бюджет сессии подписки — общий на всех
агентов (2026-07-04 три параллельных агента упёрлись в лимит, сброс
16:40 — причина ждать с четвёртым).

BDD/harness (разбор текста юзера): стандарт обсуждался ещё после v150,
но G-W-T остался прозой в карточках — исполняемого раннера не было.

OpenAI harness engineering (доки актуальны, harness верифицирует),
Cucumber-модель (требование → сценарии → исполняющий раннер),
event-driven specs — на вырост для 10k+ сценариев.

Control-center (BitGN): spec-flow по сути и есть control-center —
конституция, хартия, TAXONOMY, журналы прогонов, планы. Чего не хватало
из опыта BitGN и что берём (вписано в план, коммит 8dc4ee4):

- AGENTS.md с протоколом обнаружения («сначала tree docs, читай только
  нужное») — в корень spec-flow (сделан, 6501c81) и, главное,
  генерировать ВНУТРИ рабочей папки продукта: наши привязки становятся
  частью такого файла для воркеров;
- records/ с самомаршрутизирующимися именами (пост-мортемы, RFC,
  эксперименты) — формализовать наши runs-out и планы;
- «исполняемые описания не врут» (у него NixOS-деплой) — то же самое,
  что наш IR: правда — только то, что исполняется;
- «никаких vanity-тестов — плохие тесты = плохие требования» — ровно
  наш вывод про снятие ЛЛМ-тестера с интерфейса (узел B3), теперь
  закреплённый чужим боевым опытом;
- якорные комментарии AICODE-NOTE/TODO (greppable) — дешёвая конвенция.

Ближайшие аналоги в опенсорсе:

| Проект | Что даёт | Насколько близко |
|---|---|---|
| github/spec-kit | конституция + конвейер /specify → /clarify → /plan → /tasks → /implement | самый близкий конвейер; у нас конституция и план-гейты уже есть |
| Specmatic (+ их MCP-сервер) | OpenAPI как исполняемый контракт: тесты + stub-серверы на границах модулей; их демо самокорректирующегося цикла — ровно наша петля | прямой кирпич для узла B2 — не писать свой раннер |
| Schemathesis | property-based конформанс и фаззинг из OpenAPI | второй оракул: негативные случаи, которые мы не генерим |
| Ralph loop (awesome-ralph, ralph-orchestrator, ralph-wiggum-bdd) | петля «свежий контекст → одна задача → объективная проверка → DONE», память через git | наш пер-листовой цикл; берём свежий контекст на переспрос (узел D1) |
| AWS Kiro | requirements (EARS) / design / tasks + hooks | формат требований на заметку |
| MetaGPT, ChatDev, OpenHands, BMAD | мультиагентный SDLC | дальше — роли есть, честности и инъекций нет |

Главные правки плана из этого обзора: интерфейсную часть IR довести до
настоящего OpenAPI 3.1 (до этого было «подмножество формы» — самопал),
и тогда Specmatic+Schemathesis дают исполняемые контракты бесплатно;
свой раннер остаётся только для многошаговых сценариев (узлы A1, B1, B2).

Наша ниша, которой нет ни у кого из них разом: граф декомпозиции с
владением + детерминированная сборка + трёхслойный аудит честности +
HITL-инъекции посреди прогона. Недостающее берём из готового, не изобретаем.
