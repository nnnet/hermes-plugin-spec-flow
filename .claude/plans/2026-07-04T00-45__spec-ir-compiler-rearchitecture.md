# Переосмысление spec-flow: спека-IR как единственный источник, движок-компилятор

Дата: 2026-07-04. Контекст: v149–v164 — 16 прогонов, ~30 правил аудита,
v163 работал целиком, v164 снова сломан. Диагноз подтверждён юзером:
цель — УНИВЕРСАЛЬНЫЙ софт (каждый раз новые задачи, без памяти прошлых
проектов), спеки — единственный источник правды, независимость от
мощности модели. Кэш/инкрементальность отвергнуты как костыль-память.

## Корневая ошибка текущей архитектуры

ЛЛМ размазана по всем стадиям, стадии общаются ПРОЗОЙ. Каждая пара
прозаических артефактов — место дрейфа. Все правила S10.9–S12.16 — один
класс: «два артефакта разошлись в значении, не существовавшем как
данные». Аудит ловил рассогласования постфактум вместо их устранения
по построению. Урок v164: часть «прачечной» жила в детерминированном
коде самого движка (роутер-шаблон) — ревизия движковых шаблонов обязательна.

## Целевая форма

Единый машинный IR (структурированная спека): узлы графа + ПОЛНЫЙ
замкнутый интерфейс каждого узла (маршруты: метод/путь/статус/media/
форма запроса/форма ответа; символы с сигнатурами; конфигурация/env;
сценарии Given/When/Then первым классом). Всё, чего нет в интерфейсе, —
запрещено (закрытый мир). Из IR детерминированно КОМПИЛИРУЮТСЯ:
читаемые спеки, привязки, каркасы модулей, тесты соответствия, точка
входа, директивы лечения.

ЛЛМ ровно в двух местах:
1. описание → IR (схемная валидация + существующие план-гейты);
2. тела функций в движковом каркасе (каркас неприкосновенен — дверь).

## Граф работ

Каждый узел — по храповику: красные правила аудита ДО кода, красный И
зелёный кейс на каждый гейт. Статусы: ожидает | в работе | готов | отменён.
Исполнение: на каждом шаге искать узлы без незакрытых зависимостей и
вести их ПАРАЛЛЕЛЬНО (несколько исполнителей — каждый в своём worktree);
последовательно — только когда узлы толкаются в одних файлах.

### A1 `ir-schema` — замкнутая схема IR узла
- зависит: —
- выход: `spec_ir.py` — схема узла: `openapi` (настоящий OpenAPI 3.1:
  paths → метод → requestBody с required-полями → responses со статусом
  и media), `symbols` (exposes/consumes с сигнатурами), `env`, `files`
- приёмка: неизвестный ключ где угодно = ошибка; правила Ступени 13
  красные до кода; stdlib-only, без новых зависимостей
- статус: в работе (фоновый инженер)

### A2 `ir-scenarios` — сценарии первым классом
- зависит: A1
- выход: крошечная ЗАМКНУТАЯ схема движка (не полный Gherkin, без
  парсера-поверхности): Given {env, state} — When {method, path, body}
  — Then {status, media, body_check}; группировка по требованию
- приёмка: сценарий на маршрут вне openapi любого узла = ошибка;
  красный+зелёный кейс
- статус: в работе (фоновый инженер)

### A3 `ir-builder` — сборка IR из датумов движка
- зависит: A1
- выход: `build_ir(engine)` — слияние interface.json + contracts/
  modules.json + request_fields + media + env + владение маршрутами
  (~70% датумов уже есть); движок пишет `ir.json` в workspace
  (одна запись, событие журнала `ir_written`)
- приёмка: отсутствующий датум = честная находка-пробел, никогда не
  угаданный дефолт; изменения в движке только аддитивные
- статус: в работе (фоновый инженер)

### A4 `ir-validator` — валидатор замкнутого мира
- зависит: A1, A2, A3
- выход: проверка конформности ЦЕЛИКОМ (не аспекты по одному):
  потреблённый но не экспонированный символ; env вне деклараций;
  два владельца одного (метод, путь); маршрут у узла с детьми
- приёмка: классы v157 (фантомный `from db import store_note`) и v164
  (media-дрейф /about JSON против text/html) выражаются как именованные
  ошибки валидации; ошибки — строки с id узла и значением
- статус: в работе (фоновый инженер)

### B1 `scenario-runner` — раннер сценариев = оракул интерфейса
- зависит: A2, A3
- выход: исполнение G-W-T из IR на лету как e2e через WSGI-поверхность
  (чёрный ящик); нарушение сценария = красная сборка
- приёмка: раннер — ЕДИНСТВЕННЫЙ оракул интерфейса; поздняя инъекция =
  требование → файл сценария (красный) → реализация → зелёный (TDD-петля)
- статус: ожидает

### B2 `contract-oracle` — Specmatic + Schemathesis поверх OpenAPI из IR
- зависит: A1, A3
- выход: контрактные тесты из OpenAPI + stub-серверы на границах модулей
  (Specmatic); property-фаззинг негативных случаев (Schemathesis)
- приёмка: оба инструмента едят наш `ir.json`-производный OpenAPI без
  правок руками; свой раннер остаётся только для многошаговых сценариев
- статус: ожидает

### B3 `retire-llm-tester` — снятие ЛЛМ-тестера с интерфейса
- зависит: B1
- выход: тесты соответствия генерирует движок из IR; за ЛЛМ — только
  доменные краевые случаи сверх интерфейса (опционально)
- приёмка: класс «тестер угадал» устранён по построению; никаких
  vanity-тестов; p6 гоняется только после этого узла
- статус: ожидает

### C1 `skeleton-compiler` — каркас модуля пишет движок
- зависит: A3, A4
- выход: из IR — сигнатуры, таблица маршрутов, список разрешённых
  импортов; модель заполняет ТОЛЬКО тела функций
- приёмка: дверь записи отвергает правку каркаса; красный кейс —
  попытка модели переписать сигнатуру
- статус: ожидает

### D1 `counterexample-repair` — лечение переспросом одной функции
- зависит: C1, B1
- выход: контрпример (вход/ожидалось/получилось) → переспрос ОДНОЙ
  функции со СВЕЖИМ контекстом (петля Ральфа: одна задача за итерацию,
  объективный выход = зелёные контрактные тесты)
- приёмка: полная перепись файла невозможна по построению;
  модель-независимость через минимум степеней свободы
- статус: ожидает

### E1 `decomposer-emits-ir` — декомпозер выдаёт IR, не прозу
- зависит: A4
- выход: описание → IR со схемной валидацией на выходе декомпозера;
  существующие план-гейты работают поверх IR
- приёмка: прозаическая спека больше не является носителем интерфейса;
  невалидный IR = именованный отказ до любой сборки
- статус: ожидает

### F1 `universality-battery` — батарея случайных спек
- зависит: B3, C1, D1, E1
- выход: генератор случайных маленьких спек разных доменов; конвейер
  обязан собрать ВСЕ без памяти между ними
- приёмка: p6 перестаёт быть единственным мерилом; провал любой спеки
  из батареи = разбор по храповику
- статус: ожидает

## Что сохраняется

- Аудит: слой 1 → проверка «артефакты ↔ IR»; хартия P1–P8; ревизия
  ДВИЖКОВЫХ шаблонов (урок v164); журнал/инварианты; лаунчер/чекпойнты;
  трёхслойная схема.
- Оркестрация: параллелизм волнами, доктор (с адресацией S12.12 и
  закрытием причин S12.5), одна дверь записи, единый llm_backend.
- HITL: человек согласует поведение на уровне читаемых сценариев (G-W-T
  компилируются в читаемый вид из IR).

## Контекст и референсы (проза, не работа)

BDD/harness (разбор текста юзера): стандарт обсуждался ещё после v150,
но G-W-T остался прозой в карточках — исполняемого раннера не было.
Это корень «одноразовых вайб-планов» и разросшегося аудита. Референсы:
OpenAI harness engineering (доки актуальны, harness верифицирует),
Cucumber-модель (требование → сценарии → исполняющий раннер),
event-driven specs — на вырост для 10k+ сценариев.

Control-center (BitGN): AGENTS.md с протоколом обнаружения — сделан в
корне spec-flow (6501c81) и генерируется в воркспейсы воркеров; records/
= наши runs-out/plans/TAXONOMY; «исполняемые описания не врут» = тот же
принцип, что IR; якоря AICODE-NOTE/TODO/QUESTION; «плохие тесты =
плохие требования» — пин узла B3.

Карта аналогов опенсорса: github/spec-kit (конституция + /specify
/plan /tasks — самый близкий конвейер); AWS Kiro (EARS); Specmatic
(+specmatic-mcp-server, демо self-correcting loop = наш цикл);
Schemathesis; awesome-ralph / ralph-orchestrator; MetaGPT, ChatDev,
OpenHands, BMAD (мультиагентный SDLC — дальше); Cucumber/behave.
Наша ниша (нет ни у кого разом): граф декомпозиции с владением +
детерминированная сборка + трёхслойный аудит честности + HITL-инъекции
посреди прогона. Недостающее берём из перечисленного, не изобретаем.
