# Атомарные полные спеки + явная привязка вместо угадывания

Дата: 2026-06-29. Автор замысла: пользователь. Разбор: архитектор (Winston).

## Цель (мерило)

Из описания → детальные спеки → граф мелких → **детерминированная сборка без
угадывания**. Каждый лист настолько мал И полон, что **даже слабая модель**
выполняет его без ошибки с первого раза. Знак «готово» — честный (логическое И
всех узлов И всех заказанных адресов, включая поздние просьбы).

## Корень проблемы (что нашли в коде)

1. **Угадайка привязки.** `spec_flow_runner.py:_resolve_route_handlers` (строки
   2973–3153, ~180 строк) — машина очков, которая **догадывается**, какая функция
   за какой адрес отвечает. Привязки нет в данных спеки: имя функции каждый раз
   **вычисляется формулой** `_canonical_handler_symbol(метод, адрес)` (строка 898),
   в двух местах отдельно.
2. **Привязка даётся модели как текст-просьба**, не как закон (блок-задание
   `spec_flow_runner.py:2737–2754`: «назови функцию ровно так»). Модель отступает —
   и сборщик **не краснеет, а угадывает**.
3. **Лестница из 66 подпорок.** В `spec_flow_runner.py` — 66 ссылок на номера
   прогонов (`v020`…`v117`) в комментариях. Каждая — прогон, где угадали неверно и
   прибили заплатку. Запрещено правилом (latать угадайку ради зелёного).
4. **Атомарность судит модель и только по размеру.** `llm_decomposer.py:32–47`:
   «judge atomicity» — мягкое суждение модели; критерий — размер (≤100 строк и
   т.п.). **Полноты карточки нет:** лист не несёт точного имени функции, формы
   входа (имена параметров), формы выхода, поведения при ошибке, примеров. Мала, но
   не полна → слабой модели есть что домыслить → ошибка.
5. **Поздние просьбы — прозой**, мимо приёмки → ложный зелёный (поиск/вид были
   красные, а статус READY).

## Принцип решения

**Атомарность = мал И полон.** Лист годен, только если:
- (а) одна неделимая забота (как сейчас), И
- (б) карточка несёт ВСЁ для безошибочного исполнения: точное имя функции, форму
  входа (упорядоченные имена параметров), форму выхода, поведение при ошибке,
  1–2 примера «вход → выход», точный файл, адрес(а).

Нет полноты → это **не лист**: либо дорастить карточку, либо дробить дальше.
Слабая модель не должна ничего домысливать.

**Привязка — данные карточки, не догадка.** Имя функции на адрес вычисляется
декомпозером ОДИН раз и пишется в карточку как поле. Дальше его только **читают**:
задание модели, приёмка листа, сборка. Никогда не пересчитывают и не угадывают.

**Угадайки (пересечение слов/символов) сохранить — но ТОЛЬКО в их роли:**
проверить «существует ли такая функция уже в другом листе» (анти-дубль) и «куда
пристроить позднюю просьбу». В привязке адрес→функция при сборке они **не
участвуют**.

## Фазы

### Фаза 0 — Схема атомарной полной карточки листа

Схема обоснована образцами и стандартами (не из головы):
- образцы BMad рядом: `bmad-create-story/template.md` (история, критерии,
  ссылки), `bmad-create-epics-and-stories/templates/epics-template.md`
  (критерии «Дано→Когда→Тогда»), `bmad-create-architecture/
  architecture-decision-template.md` (контракт компонента),
  `bmad-testarch-trace/trace-template.md` (связь критерий↔тест),
  `bmad-testarch-atdd/atdd-checklist-template.md` (адрес/тело успеха/тело ошибки);
- стандарт ISO/IEC/IEEE 29148 — качества одного требования (единичность,
  однозначность, проверяемость, полнота) и набора (полнота, непротиворечивость,
  ноль «решить позже»/TBD);
- INVEST + Gherkin (Дано→Когда→Тогда) — малая, проверяемая, бинарная приёмка,
  поведение а не реализация, плохой путь тоже;
- программирование по договору (Б. Мейер) — предусловие (что даёт вызывающий) +
  постусловие (что гарантирует функция), договор как оракул теста;
- описание интерфейса службы (OpenAPI) — операция как данные: уникальное имя,
  схема тела запроса (поля+обязательные), карта «код ответа→схема», примеры.

Расширить карточку листа обязательными полями (данные, не проза), каждое — из
источника:
- `file` — точный файл `src/<stem>.py` (BMad «source tree»);
- `handler` — точное имя функции (OpenAPI: уникальное имя операции);
- `signature` — упорядоченные имена входов, напр. `["payload", "query"]`
  (договор Мейера; OpenAPI тело запроса);
- `preconditions` — что на входе обязано быть верно (предусловие Мейера; OpenAPI
  required-поля);
- `returns` / `postconditions` — форма и гарантия выхода, напр.
  «(статус:int, тело:dict)» (постусловие Мейера; OpenAPI ответ 200);
- `errors` — поведение при ошибке как данные: неизвестный путь→404, метод→405,
  кривой ввод→400 (OpenAPI карта ответов; Gherkin плохой путь);
- `acceptance` — критерии «Дано → Когда → Тогда», бинарно да/нет (Gherkin; 29148
  проверяемость);
- `examples` — 1–2 пары «вход → выход» как оракул (OpenAPI примеры; договор как
  оракул);
- `routes` — адрес(а), за которые отвечает;
- `open_decisions == 0` — ноль «решить позже» (29148: нет TBD/TBS/TBR).

Файлы:
- `tests/harness/llm_decomposer.py` — задание + схема вывода: после суждения об
  атомарности **обязать** заполнить полную карточку; пустые поля = не атомарен.
- `tests/harness/blueprint_decomposer.py` — guardrail атомарности расширить с
  «single_concern/testable_criteria» на **полноту карточки**.
- `spec_flow_runner.py:_lint_spec_traceability` (210) — детерминированный гейт:
  лист без полной карточки = красный (с понятной причиной), не пропускать.

### Фаза 1 — Привязка как данные (один раз, потом только чтение)
- Декомпозер пишет `handler` в карточку через `_canonical_handler_symbol` **на
  этапе декомпозиции** (один раз).
- Блок-задание модели `spec_flow_runner.py:2737–2754` читает `card.handler` из
  карточки, **не пересчитывает**.
Файлы: `spec_flow_runner.py` (2737–2754), декомпозер (Фаза 0).

### Фаза 2 — Жёсткий гейт листа по карточке (да/нет)
Детерминированная проверка (по дереву кода, без запуска): модуль определяет
функцию **ровно** с именем `card.handler` и формой `card.signature`, возвращает
заявленную форму. Нет → лист **красный** → переспросить **ровно его** с той же
атомарной карточкой (можно усилить модель). **Без угадывания за модель.**
Файлы: `spec_flow_runner.py:_judge_leaf` (1923), `_review_gate` (4418),
`_verify_once` (5295).

### Фаза 3 — Сборка читает карту привязок; угадайку удалить
- `_synthesize_entry_code` (3155) строит роутер из **карты привязок** (свод
  карточек листьев): адрес → `handler` из его листа. Прямое чтение.
- **Удалить** `_resolve_route_handlers` (2973–3153) — всю машину очков и её
  путь-фолбэк. Вместе с ней уходят 66 подпорок. Если лист не дал свой `handler` —
  это красный лист (Фаза 2), а не повод угадывать на сборке.
- `_harvest_entry_handlers` — оставить лишь подключение по карте, без поиска
  «где бы модель ни написала».
Файлы: `spec_flow_runner.py` (2973, 3155, харвест).

### Фаза 4 — Обособить детекторы пересечения под их роль
`_amd_symbol_overlap` / `_amd_token_overlap` (945–957) и маршрутизация поздних
просьб — оставить, но **только** для: (а) анти-дубль (функция уже есть в другом
листе?), (б) выбор модуля для поздней просьбы. Убедиться, что в привязке
адрес→функция при сборке (Фаза 3) они **не используются**. При нужде — чёткое имя,
обособляющее их от сборки.
Файлы: `spec_flow_runner.py` (детекторы + путь поздних инъекций).

### Фаза 5 — Поздние просьбы → атомарные полные карточки
Поздняя просьба (поиск, красивый вид) превращается в **атомарный лист с полной
карточкой** (Фаза 0) ДО сборки, а не остаётся прозой. Проходит тот же гейт
(Фаза 2) и попадает в карту привязок (Фаза 3).
Файлы: `spec_flow_runner.py:_late_req_delta_gate` (2119), `_requirement_nodes`
(1990).

### Фаза 6 — Детерминированный гейт плана декомпозиции (закрывает #105)
Перед сборкой проверить план как данные:
- у каждого объявленного адреса **ровно один** лист-владелец с полной карточкой;
- нет адреса без владельца; нет двух владельцев;
- нет листа без полной карточки.
Это качества НАБОРА требований по ISO/IEC/IEEE 29148: полнота (нет адреса без
владельца), непротиворечивость (нет двух владельцев), ноль «решить позже».
Не сошлось → честный красный с причиной (не угадывать). Это и есть pending-задача
#105.
Файлы: `spec_flow_runner.py` (новый гейт у `_default_decomposer`/валидации плана).

### Фаза 7 — Честное «готово» + чистка
- Финальный статус прогона = И(все листья прошли гейт) И(все адреса служат,
  включая поздние). См. память `specflow_ready_is_conjunction`.
- Вернуть `product_repair_rounds` 6 → 3: при честных красных листьях и переспросе
  лестница лечений не нужна.
Файлы: `spec_flow_runner.py` (терминальный статус, `product_repair_rounds`),
`tests/lib/run_cases.py` (штамп `meta.status`).

## Проверка
1. Офлайн-набор после каждой фазы: `pytest tests/coverage tests/dashboard
   tests/harness` + новые репро-тесты (полнота карточки; гейт листа да/нет; сборка
   по карте; гейт плана).
2. Репро в `tests/coverage/test_entry_synthesis.py`: модель «ошиблась именем» →
   лист честно красный и переспрошен, путь-угадайка **не вызывается**.
3. Один отвязанный прогон p6 (`tests/run-detached.sh`): ждём — модель отступила →
   честный красный лист → переспрос; **нет** пути угадывания; READY только когда
   все листья + все адреса (вкл. поздние) служат.

## Что НЕ трогаем
- Параллелизм — не выключать. Платное — не включать.
- Детекторы пересечения — НЕ удалять (нужны для анти-дубля и поздних просьб),
  только обособить от сборки.
- Защиты от ложно-зелёного (boot-oracle, дельта-гейт) — остаются.

## Запреты (память)
- Не латать угадайку ради зелёного (`feedback_no_masking_engine_glue_patches`).
- Не облегчать тесты, не подкладывать ответы (`feedback_never_scaffold_tests_to_pass`).
- Честное «готово» = логическое И (`specflow_ready_is_conjunction`).
