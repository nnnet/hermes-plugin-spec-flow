# Ретроспектива промышленного теста p5 «работающий MVP» + план улучшений

Дата: 2026-06-12. Критерий успеха (задан жёстко): **только работающий
маркетплейс = успешный тест**. Взято на v14: корневая интеграция PASS на
настоящем pytest, 54 теста зелёные, включая сквозной смоук на собранном
приложении (продавец → товар → поиск → оплаченный заказ → выплата).
Артефакты: `tests/runs-out/2026-06-12T09-55-54__p5-mvp-marketplace/`.

---

## Часть 1. Что было сделано, какие недостатки устранены и что это дало

Хронология витков. Каждый виток = прогон → разбор провала → фикс класса
ошибки (не симптома) → регрессионный тест → коммит → новый прогон.

### Шаг 0. Фундамент: критерий успеха стал материальным
**Недостаток:** вердикт интеграции выносила модель-проверщик — мнение,
а не факт; «зелёный» прогон мог не содержать работающего продукта.
**Сделано:** `harness/pytest_verifier.py` — вердикт каждого integrate-гейта
= код возврата настоящего `pytest`; кейс p5 несёт затравочный каркас
(WSGI-вход `app.py`, реестр маршрутов `registry.py`, sqlite-обвязка
`db.py`) и смоук-сценарий `tests/smoke/`, который и есть приёмка; смоук
гейтит только корень (частичная сборка его не проходит по определению).
**Зачем:** без этого «успех» недоказуем.
**Дало:** все последующие провалы стали честными и диагностируемыми;
машина приёмки проверена эталонными фичами, написанными руками, до
первого прогона.

### Шаг 1 (v2). Затравка переживает старт прогона
**Недостаток:** движок при старте сметает каталог workspace — затравка,
записанная обвязкой заранее, уничтожалась; v1 «прошёл» без каркаса и
смоука (ложный зелёный).
**Сделано:** `seed_files` — понятие движка: `run_project(seed_files=...)`
→ `Workspace.open()` пишет их ПОСЛЕ очистки, в манифест, с защитой от
выхода за каталог.
**Дало:** платформа гарантированно присутствует в каждом прогоне.

### Шаг 2 (v3). Затравка неприкосновенна
**Недостаток:** воркер переписал `src/app.py` собственным монолитом с
конфликтующей схемой — сборка умерла.
**Сделано:** `SPEC_FLOW_PROTECTED_FILES` (из списка затравки кейса) —
оба писателя (реализатор и починка интеграции) ОТКАЗЫВАЮТ в записи в
платформенные файлы, с журналируемым `write_refused`; плюс правило в
промпте.
**Дало:** каркас стабилен; фичи строятся В него, а не ВМЕСТО него.

### Шаг 3 (v4). Контракт сигнатур + починка видит весь src
**Недостаток:** обработчик принял 1 аргумент вместо платформенных
`(payload, query)` — лист зелёный у себя, мёртвый в сборке; починка не
смогла помочь: в красном выводе не было имени файла-виновника.
**Сделано:** сигнатура прибита в контракте реализатора (и в его
собственных тестах); `_implicated_files` при провале без имён файлов
вкладывает ВСЕ доступные src-модули.
**Дало:** v6 уже регистрировал продавца сквозь приложение.

### Шаг 4 (v5). Сквозные тесты — собственность платформы
**Недостаток:** декомпозер строил листья «smoke harness» / «test
fixtures» — дубли приёмки среди обычных тестов, честно красные на каждой
частичной сборке; плюс кольцевой импорт (`test_fixtures` импортировал
`app` обратно).
**Сделано:** декомпозеру — «дели по фичам продукта, не по фазам
тестирования»; реализатору — «тестируй только свой модуль; фича
импортирует только registry, db и stdlib, никогда app».
**Дало:** деревья стали фичевыми, сборка перестала умирать на импорте.

### Шаг 5 (v6). Полнота контракта + починка читает приёмку
**Недостаток:** декомпозер терял целые фичи (заказы, выплаты) — продукт
собирался без половины ручек; починка не видела требуемый API (смоук был
исключён из чтения как защищённый) и не знала, что надо ДОПИСАТЬ фичу.
**Сделано:** правило «каждая ручка замороженного контракта принадлежит
ровно одному листу»; `_readonly_context` — защищённые файлы из провала
вкладываются в починку как read-only («удовлетвори, не правь»); провал
«no route» получает явное указание создать новый модуль.
**Дало:** с v9 все нужные фичи существуют в каждом прогоне.

### Шаг 6 (v7). Видимость чужих схем → карта репозитория
**Недостаток:** две фичи объявляли одну таблицу с разными колонками;
`CREATE IF NOT EXISTS` оставляет первую — чужие запросы умирают. Лист
не видит соседей.
**Сделано (по заказу пользователя, обобщение по образцу aider):**
`harness/repo_map.py` — AST-дайджест публичной поверхности каждого
модуля (докстринг, маршруты дословно, SQL схем, сигнатуры классов и
функций), пересобирается вживую, бюджетируется. Потребители: реализатор
(полная карта), декомпозер (карта src — «дополняй поверхность, не
дублируй»), починка (полкарты).
**Дало:** главный механизм против слепоты, заменил три точечных вставки.

### Шаг 7 (v8). Мусорный ответ не убивает прогон
**Недостаток:** одна не-JSON реплика реализатора валила весь прогон
исключением парсера.
**Сделано:** `_extract_json` срезает код-заборы и перебирает все позиции
скобок; реализатор при мусоре делает один строгий повторный запрос и
затем честно сдаёт лист красным (гейт поймает).
**Дало:** прогоны перестали гибнуть от единичной флуктуации модели.

### Шаг 8 (v9–v10). Контракт стал полным: статусы и формы
**Недостаток:** воркеры не видят текст смоука, а в конституции не было
статусов (вернул 200 вместо 201) и форм запросов (ждал `name/description`
вместо `title`).
**Сделано:** конституция кейса несёт ВЕСЬ контракт: ручки, статусы
(POST=201/GET=200), формы ответов и точные поля запросов.
**Дало:** v11 — смоук ЗЕЛЁНЫЙ впервые (вся цепочка работает).

### Шаг 9 (v11). Починка не ухудшает и оставляет след
**Недостаток (ранее, проявилось в v2-серии):** раунд починки переписал
модуль и оставил устаревший тест — сборка стала хуже, чем была; первый
красный вывод терялся.
**Сделано:** каждый раунд снимает слепок перезаписываемых файлов и
ОТКАТЫВАЕТСЯ, если балл провала вырос (ошибка сборки = худшее);
`integrate_red` пишет первый красный вывод в журнал; правило «устаревший
тест: восстанови API или обнови тест».
**Дало:** монотонность — дерево после починки никогда не хуже, чем до.

### Шаг 10 (v13). Внутренности платформы под замком
**Недостаток:** лист «изолировал» свои тесты вызовом
`db._SCHEMAS.clear()` — стирал схемы всех соседей до конца сессии
(в одиночку зелёный, в наборе — отравитель).
**Сделано:** `content_allowed()` — записи, трогающие `_SCHEMAS` /
`ROUTES.clear()`, отказываются обоими писателями; изоляция теста =
свежий `MARKETPLACE_DB`, и только.
**Дало:** v14 — полный зелёный набор, MVP взят.

### Шаг 11 (параллельно). Контур моделей по жёсткому правилу
**Недостаток:** воркеры сидели на платном `claude haiku` как на основном
пути; фолбэк ходил через шлюз и умирал об его 403/500.
**Сделано:** единая дверь `llm_backend.ask()`: только `:free` модели
OpenRouter (платная = ошибка без `SPEC_FLOW_ALLOW_PAID=1`), при
исчерпании — фолбэк haiku НАПРЯМУЮ в подписку (мимо шлюза), выдержка
10 минут с авто-возвратом на бесплатный пул; `last_call` фиксирует, кто
реально обслужил вызов.
**Дало:** весь тест выполнен на бесплатном пуле (фолбэк понадобился
эпизодически), правило закреплено кодом и памятью.

### Сквозные уроки (формула)
1. Контекст воркерам — передавать механически (карта, контракт, схемы),
   а не надеяться, что модель «догадается».
2. Дисциплина — детерминированными гейтами (настоящий pytest,
   неприкосновенные файлы, отказ в опасной записи, откат ухудшения),
   промпт — лишь профилактика частоты.
3. Модель ненадёжна по умолчанию: любой её выход — кандидат, который
   проверяется и может быть отвергнут без ущерба для прогона.

## Часть 2. Что можно улучшить (план)

### П1. Перенести наработки из тестовой обвязки в продукт
Карта репозитория, неприкосновенные файлы, контракт сигнатур, гейт
платформенных внутренностей живут в `tests/harness/` — а боевой режим
(воркеры Гермеса с тулзами) получит те же классы ошибок. Нужно:
- `repo_map.py` → в сам плагин (движок отдаёт карту в контекст любому
  воркеру через ctx);
- protected-files и content-гейт → в движок как политику workspace,
  а не env тестовой обвязки;
- spec-flow skills дополнить правилами «фича строится в платформу»,
  когда кейс несёт затравку.

### П2. Авто-вывод контракта из смоука
Сейчас контракт продублирован руками в конституции (ручки, статусы,
формы) — источник дрейфа. Улучшение: парсить смоук (AST: вызовы
`call(...)` и assert'ы) и генерировать контрактный блок автоматически;
конституция ссылается на сгенерированное.

### П3. Точечная починка вместо «весь файл целиком»
Починка переписывает файлы целиком — дорого и рискованно. Улучшение:
формат диффа (anchor-replace как в Edit-инструментах) с валидацией
применимости; неприменимый дифф = отказ без записи.

### П4. Бисекция отравителей в верификаторе
Класс «зелёный в одиночку, красный в наборе» диагностировался руками
(пары файлов). Улучшение: при красном наборе с зелёными одиночками
верификатор сам бисектит набор и называет файл-отравитель в детали
провала — починка получает точную цель.

### П5. Параллелизм листьев
Листья одной ветки независимы, а исполняются последовательно (~5-7 мин
на лист). Движок уже знает зависимости; пул из 2-3 воркеров сократит
прогон в разы. Осторожно: гонки за квоту бесплатного пула.

### П6. Экономика прогона
COST.json есть, но не агрегируется по виткам. Улучшение: сводка
запросов/токенов на роль и на виток, лимит запросов на прогон
(глобальный бюджет, не только на узел), алерт при приближении к 1000/день.

### П7. Усиление ревью артефактами
Ревьюер судит только текст спеки. Дать ему карту репозитория и список
write_refused/rolled_back событий узла — ловить архитектурные конфликты
до реализации, а не после.

### П8. Спайк-исследования на сильной модели
Researcher на free-модели даёт поверхностные рекомендации. Спайки редки
(1-2 на прогон) — допустить для них haiku/sonnet по явному флагу кейса:
дорогая модель там, где решение дороже токенов.

### П9. Возобновляемость прогона
Прогон, упавший на тике 60, начинается с нуля. Движок имеет resume для
workspace; довести до конца: журнал состояния дерева + пропуск уже
PASS-нутых узлов при рестарте с тем же кейсом.

### П10. Несколько смоук-сценариев
Один сценарий = одна счастливая тропа. Добавить в `tests/smoke/`
негативные: отказ KYC-заглушки, покупка несуществующего товара, поиск
без результатов — рост честности приёмки без роста дерева.
