# Ретроспектива промышленного теста p5 «работающий MVP» + план улучшений

Дата: 2026-06-12. Критерий успеха (задан жёстко): **только работающий
маркетплейс = успешный тест**. Взято на v14: корневая интеграция PASS на
настоящем pytest, 54 теста зелёные, включая сквозной смоук на собранном
приложении (продавец → товар → поиск → оплаченный заказ → выплата).
Артефакты: `tests/runs-out/2026-06-12T09-55-54__p5-mvp-marketplace/`.

---

## Часть 1. Что было сделано, какие недостатки устранены и что это дало

Хронология витков. Каждый виток = прогон → разбор провала → фикс класса
ошибки (не симптома) → регрессионный тест → коммит → новый прогон.

### Шаг 0. Фундамент: критерий успеха стал материальным
**Недостаток:** вердикт интеграции выносила модель-проверщик — мнение,
а не факт; «зелёный» прогон мог не содержать работающего продукта.
**Сделано:** `harness/pytest_verifier.py` — вердикт каждого integrate-гейта
= код возврата настоящего `pytest`; кейс p5 несёт затравочный каркас
(WSGI-вход `app.py`, реестр маршрутов `registry.py`, sqlite-обвязка
`db.py`) и смоук-сценарий `tests/smoke/`, который и есть приёмка; смоук
гейтит только корень (частичная сборка его не проходит по определению).
**Зачем:** без этого «успех» недоказуем.
**Дало:** все последующие провалы стали честными и диагностируемыми;
машина приёмки проверена эталонными фичами, написанными руками, до
первого прогона.

### Шаг 1 (v2). Затравка переживает старт прогона
**Недостаток:** движок при старте сметает каталог workspace — затравка,
записанная обвязкой заранее, уничтожалась; v1 «прошёл» без каркаса и
смоука (ложный зелёный).
**Сделано:** `seed_files` — понятие движка: `run_project(seed_files=...)`
→ `Workspace.open()` пишет их ПОСЛЕ очистки, в манифест, с защитой от
выхода за каталог.
**Дало:** платформа гарантированно присутствует в каждом прогоне.

### Шаг 2 (v3). Затравка неприкосновенна
**Недостаток:** воркер переписал `src/app.py` собственным монолитом с
конфликтующей схемой — сборка умерла.
**Сделано:** `SPEC_FLOW_PROTECTED_FILES` (из списка затравки кейса) —
оба писателя (реализатор и починка интеграции) ОТКАЗЫВАЮТ в записи в
платформенные файлы, с журналируемым `write_refused`; плюс правило в
промпте.
**Дало:** каркас стабилен; фичи строятся В него, а не ВМЕСТО него.

### Шаг 3 (v4). Контракт сигнатур + починка видит весь src
**Недостаток:** обработчик принял 1 аргумент вместо платформенных
`(payload, query)` — лист зелёный у себя, мёртвый в сборке; починка не
смогла помочь: в красном выводе не было имени файла-виновника.
**Сделано:** сигнатура прибита в контракте реализатора (и в его
собственных тестах); `_implicated_files` при провале без имён файлов
вкладывает ВСЕ доступные src-модули.
**Дало:** v6 уже регистрировал продавца сквозь приложение.

### Шаг 4 (v5). Сквозные тесты — собственность платформы
**Недостаток:** декомпозер строил листья «smoke harness» / «test
fixtures» — дубли приёмки среди обычных тестов, честно красные на каждой
частичной сборке; плюс кольцевой импорт (`test_fixtures` импортировал
`app` обратно).
**Сделано:** декомпозеру — «дели по фичам продукта, не по фазам
тестирования»; реализатору — «тестируй только свой модуль; фича
импортирует только registry, db и stdlib, никогда app».
**Дало:** деревья стали фичевыми, сборка перестала умирать на импорте.

### Шаг 5 (v6). Полнота контракта + починка читает приёмку
**Недостаток:** декомпозер терял целые фичи (заказы, выплаты) — продукт
собирался без половины ручек; починка не видела требуемый API (смоук был
исключён из чтения как защищённый) и не знала, что надо ДОПИСАТЬ фичу.
**Сделано:** правило «каждая ручка замороженного контракта принадлежит
ровно одному листу»; `_readonly_context` — защищённые файлы из провала
вкладываются в починку как read-only («удовлетвори, не правь»); провал
«no route» получает явное указание создать новый модуль.
**Дало:** с v9 все нужные фичи существуют в каждом прогоне.

### Шаг 6 (v7). Видимость чужих схем → карта репозитория
**Недостаток:** две фичи объявляли одну таблицу с разными колонками;
`CREATE IF NOT EXISTS` оставляет первую — чужие запросы умирают. Лист
не видит соседей.
**Сделано (по заказу пользователя, обобщение по образцу aider):**
`harness/repo_map.py` — AST-дайджест публичной поверхности каждого
модуля (докстринг, маршруты дословно, SQL схем, сигнатуры классов и
функций), пересобирается вживую, бюджетируется. Потребители: реализатор
(полная карта), декомпозер (карта src — «дополняй поверхность, не
дублируй»), починка (полкарты).
**Дало:** главный механизм против слепоты, заменил три точечных вставки.

### Шаг 7 (v8). Мусорный ответ не убивает прогон
**Недостаток:** одна не-JSON реплика реализатора валила весь прогон
исключением парсера.
**Сделано:** `_extract_json` срезает код-заборы и перебирает все позиции
скобок; реализатор при мусоре делает один строгий повторный запрос и
затем честно сдаёт лист красным (гейт поймает).
**Дало:** прогоны перестали гибнуть от единичной флуктуации модели.

### Шаг 8 (v9–v10). Контракт стал полным: статусы и формы
**Недостаток:** воркеры не видят текст смоука, а в конституции не было
статусов (вернул 200 вместо 201) и форм запросов (ждал `name/description`
вместо `title`).
**Сделано:** конституция кейса несёт ВЕСЬ контракт: ручки, статусы
(POST=201/GET=200), формы ответов и точные поля запросов.
**Дало:** v11 — смоук ЗЕЛЁНЫЙ впервые (вся цепочка работает).

### Шаг 9 (v11). Починка не ухудшает и оставляет след
**Недостаток (ранее, проявилось в v2-серии):** раунд починки переписал
модуль и оставил устаревший тест — сборка стала хуже, чем была; первый
красный вывод терялся.
**Сделано:** каждый раунд снимает слепок перезаписываемых файлов и
ОТКАТЫВАЕТСЯ, если балл провала вырос (ошибка сборки = худшее);
`integrate_red` пишет первый красный вывод в журнал; правило «устаревший
тест: восстанови API или обнови тест».
**Дало:** монотонность — дерево после починки никогда не хуже, чем до.

### Шаг 10 (v13). Внутренности платформы под замком
**Недостаток:** лист «изолировал» свои тесты вызовом
`db._SCHEMAS.clear()` — стирал схемы всех соседей до конца сессии
(в одиночку зелёный, в наборе — отравитель).
**Сделано:** `content_allowed()` — записи, трогающие `_SCHEMAS` /
`ROUTES.clear()`, отказываются обоими писателями; изоляция теста =
свежий `MARKETPLACE_DB`, и только.
**Дало:** v14 — полный зелёный набор, MVP взят.

### Шаг 11 (параллельно). Контур моделей по жёсткому правилу
**Недостаток:** воркеры сидели на платном `claude haiku` как на основном
пути; фолбэк ходил через шлюз и умирал об его 403/500.
**Сделано:** единая дверь `llm_backend.ask()`: только `:free` модели
OpenRouter (платная = ошибка без `SPEC_FLOW_ALLOW_PAID=1`), при
исчерпании — фолбэк haiku НАПРЯМУЮ в подписку (мимо шлюза), выдержка
10 минут с авто-возвратом на бесплатный пул; `last_call` фиксирует, кто
реально обслужил вызов.
**Дало:** весь тест выполнен на бесплатном пуле (фолбэк понадобился
эпизодически), правило закреплено кодом и памятью.

### Сквозные уроки (формула)
1. Контекст воркерам — передавать механически (карта, контракт, схемы),
   а не надеяться, что модель «догадается».
2. Дисциплина — детерминированными гейтами (настоящий pytest,
   неприкосновенные файлы, отказ в опасной записи, откат ухудшения),
   промпт — лишь профилактика частоты.
3. Модель ненадёжна по умолчанию: любой её выход — кандидат, который
   проверяется и может быть отвергнут без ущерба для прогона.

## Часть 2. Что можно улучшить (план)

### П1. Перенести наработки из тестовой обвязки в продукт
Карта репозитория, неприкосновенные файлы, контракт сигнатур, гейт
платформенных внутренностей живут в `tests/harness/` — а боевой режим
(воркеры Гермеса с тулзами) получит те же классы ошибок. Нужно:
- `repo_map.py` → в сам плагин (движок отдаёт карту в контекст любому
  воркеру через ctx);
- protected-files и content-гейт → в движок как политику workspace,
  а не env тестовой обвязки;
- spec-flow skills дополнить правилами «фича строится в платформу»,
  когда кейс несёт затравку.

### П2. Авто-вывод контракта из смоука
Сейчас контракт продублирован руками в конституции (ручки, статусы,
формы) — источник дрейфа. Улучшение: парсить смоук (AST: вызовы
`call(...)` и assert'ы) и генерировать контрактный блок автоматически;
конституция ссылается на сгенерированное.

### П3. Точечная починка вместо «весь файл целиком»
Починка переписывает файлы целиком — дорого и рискованно. Улучшение:
формат диффа (anchor-replace как в Edit-инструментах) с валидацией
применимости; неприменимый дифф = отказ без записи.

### П4. Бисекция отравителей в верификаторе
Класс «зелёный в одиночку, красный в наборе» диагностировался руками
(пары файлов). Улучшение: при красном наборе с зелёными одиночками
верификатор сам бисектит набор и называет файл-отравитель в детали
провала — починка получает точную цель.

### П5. Параллелизм листьев
Листья одной ветки независимы, а исполняются последовательно (~5-7 мин
на лист). Движок уже знает зависимости; пул из 2-3 воркеров сократит
прогон в разы. Осторожно: гонки за квоту бесплатного пула.

### П6. Экономика прогона
COST.json есть, но не агрегируется по виткам. Улучшение: сводка
запросов/токенов на роль и на виток, лимит запросов на прогон
(глобальный бюджет, не только на узел), алерт при приближении к 1000/день.

### П7. Усиление ревью артефактами
Ревьюер судит только текст спеки. Дать ему карту репозитория и список
write_refused/rolled_back событий узла — ловить архитектурные конфликты
до реализации, а не после.

### П8. Спайк-исследования на сильной модели
Researcher на free-модели даёт поверхностные рекомендации. Спайки редки
(1-2 на прогон) — допустить для них haiku/sonnet по явному флагу кейса:
дорогая модель там, где решение дороже токенов.

### П9. Возобновляемость прогона
Прогон, упавший на тике 60, начинается с нуля. Движок имеет resume для
workspace; довести до конца: журнал состояния дерева + пропуск уже
PASS-нутых узлов при рестарте с тем же кейсом.

### П10. Несколько смоук-сценариев
Один сценарий = одна счастливая тропа. Добавить в `tests/smoke/`
негативные: отказ KYC-заглушки, покупка несуществующего товара, поиск
без результатов — рост честности приёмки без роста дерева.

## Часть 3. Обзор изученных сторонних опенсорсных фреймворков

Контекст оценки: тестируемый продукт — наш собственный конвейер
(движок spec-flow + умения + профили), поэтому «взять фреймворк целиком»
почти всегда означало бы тестировать чужой конвейер вместо своего.
Заимствовались подходы, не зависимости.

| Фреймворк | Почему не был / был использован целиком | Какая часть использована в плагине | Что ещё может быть использовано | Что не подходит и почему |
|---|---|---|---|---|
| **aider** | Не целиком: это интерактивный CLI-помощник для человека, не конвейер ролей | **Карта репозитория** — главное заимствование: AST-дайджест публичной поверхности всех модулей в каждый промпт (`harness/repo_map.py`; у aider — tree-sitter) | Формат диффов для правок (search/replace-блоки) → П3; ранжирование карты по релевантности узлу (у aider — graph-ranking) | Интерактивная петля с человеком в центре — у нас воркеры автономны; tree-sitter как зависимость не нужен (workspace чисто Python, хватает ast) |
| **MetaGPT** | Не целиком: его конвейер (PRD→дизайн→задачи→код) дублирует наш движок — это конкурент spec-flow, а не компонент | Подход «стандартизованные артефакты между ролями»: наши спеки с EARS-требованиями, Traces-to и замороженные контракты — та же школа, реализованная движком | Идея «общей доски» (shared message pool) для асинхронного обмена находками между воркерами — при параллелизме листьев (П5) | SOP-сценарии ролей зашиты в их код — у нас роли определяются SKILL.md/профилями плагина, подменять их чужими нельзя: тест перестал бы проверять наш продукт |
| **OpenHands (OpenDevin)** | Не целиком: тяжёлый рантайм (docker-песочницы, свой сервер) ради того, что в проде даст Гермес | Принцип «агенту — настоящие руки + проверка исполнением»: наш pytest-верификатор и запуск тестов листа обвязкой | Их ACI-паттерн (структурированный интерфейс агент-компьютер) — образец для боевого режима воркеров Гермеса с тулзами | Песочница и оркестрация дублируют инфраструктуру Hermes; в тестовом чат-режиме «руки» запрещены правилом бесплатных моделей |
| **SWE-agent** | Не целиком: заточен под решение GitHub-issue в существующем репозитории, не под строительство продукта с нуля | Дисциплина «фидбэк от реального запуска — в следующий промпт»: наши раунды починки с хвостом pytest-вывода | Их вывод «интерфейс важнее модели» (ACI) — аргумент за П1 (перенос гейтов в плагин); компактные форматы ошибок | Однo-агентная модель без декомпозиции — у нас многоуровневое дерево с гейтами на каждом узле |
| **ChatDev** | Не целиком: «виртуальная софтверная компания» с чат-цепочками — снова конкурент конвейера | Парная петля «писатель↔критик»: наше ревью спеки с доработкой (REJECT → spec-only rework → повторное ревью) | Их «коммуникативное обеззараживание» (dehallucination через переспрос) — для диалогового HITL | Роли и фазы зашиты; обмен — неструктурированный чат, у нас — структурированные артефакты и JSON-контракты |
| **gpt-pilot / GPT-Engineer** | Не целиком: монолитные генераторы проекта, без канбана, гейтов и методологии | Подход gpt-pilot «строить инкрементально с тестами после каждого шага» — наш TDD-контракт реализатора | Их приём «уточняющие вопросы до старта» — уже есть в desire-to-goal; сверить полноту списков вопросов | Нет ревью/аудита/трассировки требований — то, ради чего spec-flow существует |
| **AgentCoder** | Не целиком: исследовательский прототип (3 агента вокруг одной функции) | Разделение «автор кода ≠ автор тестов ≠ исполнитель»: у нас смоук от платформы, тесты листа от воркера, вердикт от детерминированного раннера | Идея отдельного агента-генератора тестов для П10 (негативные смоук-сценарии) | Масштаб функции, не продукта; нет понятия workspace |
| **CrewAI / AutoGen / LangGraph** | Не использованы: фреймворки оркестрации агентов — а оркестратор у нас и есть тестируемый движок | Ничего напрямую | LangGraph-паттерн «чекпойнт состояния графа» — образец для П9 (возобновляемость прогона) | Подменяют ядро продукта; тянут тяжёлые зависимости и свои абстракции LLM-вызовов поверх нашего llm_backend с правилом бесплатного пула |

Вывод: индустрия сошлась на тех же трёх опорах, что выкристаллизовал наш
тест — (1) механическая передача контекста (карта репозитория), (2)
структурированные артефакты между ролями (спеки/контракты), (3) вердикт
реальным исполнением с петлёй починки. Всё это в плагине уже есть своё;
заимствовать осталось точечные приёмы: дифф-формат правок (aider),
чекпойнты графа (LangGraph), генератор негативных тестов (AgentCoder).

### П11. Политика on_integrate_fail (по вопросу пользователя 2026-06-12)
Сейчас провал интеграции ветки записывается, и прогон продолжается до
корня (осознанный дефолт: соседние ветки независимы, корень не позеленеет
без устранения). Сделать выбор явным, по аналогии с review-политикой:
`integrate: {on_fail: record|rework|halt}` в YAML кейса — record (как
сейчас), rework (расширенный бюджет починки на самой ветке), halt
(остановить прогон на первом красном integrate). Дополняет двухъярусную
планку листа (свои тесты + неухудшение набора), которая уже сдвинула
обнаружение межфичевых поломок к листу-виновнику.

## Часть 4. План параллелизации работы плагина

Сейчас движок строго последователен: в каждый момент развивается один
узел (декомпозиция → спека → ревью → листья по одному → интеграция).
При этом ~95% стенного времени — ожидание ответа модели, то есть
параллелизм почти целиком — параллелизм ОЖИДАНИЯ, не вычислений. Это
определяет архитектуру: движок остаётся однопоточным владельцем
состояния (дерево, FSM, журнал), в пул уходят только вызовы воркеров.

### Варианты параллелизации (от дешёвого к глубокому)

**В1. Параллельные листья одной ветки.** Листья по построению
одно-концерные и независимые (свой модуль + свои тесты). После того как
ВСЕ спеки листьев ветки прошли ревью — реализаторы запускаются пулом
(2–4). Самый большой выигрыш: листья — длиннейшая фаза прогона.

**В2. Конвейер фаз между соседними узлами.** Пока ревьюер судит спеку
узла A, декомпозер уже пишет уровень узла B; пока листья ветки A
реализуются, ветка B декомпозируется. Роли заняты одновременно, но
каждый узел проходит фазы в своём строгом порядке.

**В3. Параллельные ветки уровня.** Сёстры-ветки (онбординг ↔ каталог ↔
заказы) развиваются целиком параллельно; интеграции — по готовности,
корень ждёт всех. Максимальный риск перекрёстных конфликтов — только
после В1+В2 и резерваций (см. ниже).

**В4. Спекулятивные спайки.** Research-вопросы уровня выполняются
параллельно с написанием спеки (рекомендация вливается до заморозки).
Дёшево и безопасно: спайк ничего не пишет в workspace.

### Конфликты и как их избегать

**К1. Два листа пишут один файл / одну таблицу.** Прямой конфликт
файлов уже исключён писателями (лист может писать только src/<свой>.py
и tests/test_<свой>.py). Косвенный — таблицы и маршруты. Решение:
**спека = резервация**. Спеки листьев пишутся ДО реализации (spec-first
— наше преимущество): в момент одобрения спек ветки движок собирает
объявленные маршруты/таблицы и детерминированным гейтом отвергает
пересечения (то, что сейчас ловится картой репозитория постфактум,
становится невозможным до старта реализации).

**К2. Гонка за общий тестовый набор (планка листа).** Двухъярусная
планка сравнивает «набор до/после» — при параллельных листьях набор
движется. Решение: **очередь фиксации** (merge queue, как в CI):
реализатор работает в стороне, по готовности лист встаёт в очередь;
фиксация (запись файлов + прогон набора + планка) — строго по одному,
с откатом неудачника обратно в доработку. Реализация дешёвая: один
mutex на «фиксацию листа» — модельные сессии остаются параллельными,
сериализуется только секундный pytest.

**К3. Карта репозитория слепа к незафиксированным соседям.** Параллельный
лист не видит код соседа, которого ещё нет. Решение: карта дополняется
блоком «in progress» из РЕЗЕРВАЦИЙ (маршруты/таблицы/сигнатуры из уже
одобренных спек) — соседи видны до того, как написан их код.

**К4. Квота моделей.** Параллельные сессии умножают 429 бесплатного
пула. Решение: глобальный ограничитель в llm_backend (семафор N
одновременных + общий счётчик к суточному лимиту + один общий cooldown
на пул, чтобы N воркеров не пробивали его параллельно).

**К5. Журналы и состояние движка.** trace/llm-log пишутся из потоков.
Решение: единственный писатель — поток движка; воркеры возвращают
результаты через футуры, движок сам пишет журнал (тики остаются
монотонными, дашборд не меняется).

**К6. Недетерминизм порядка.** Параллельный прогон не воспроизводим
по тикам. Решение: журнал получает идентификатор узла-источника у
каждого события (уже есть task) + поле wave; аудит правил (R1–R9)
проверяет порядок ВНУТРИ узла, не между узлами — правки аудита
минимальны.

### Пошаговый план

**Этап 0 — измерение (полдня).** Профиль текущего прогона: время по
фазам и ролям из llm-log (call_start→outcome). Подтвердить долю
ожидания модели; зафиксировать базовую длительность p5 (~35–50 мин) и
p4 (~2 ч) как эталон ускорения.

**Этап 1 — резервации без параллелизма (1 день).** Спеки листьев
объявляют маршруты/таблицы; движок: гейт уникальности на одобрении спек
ветки + блок «in progress» в карте. Польза немедленно (класс коллизий
умирает до кода), и это пререквизит В1/В3.

**Этап 2 — В1: параллельные листья (2 дня).** Пул реализаторов
(SPEC_FLOW_PARALLEL_LEAVES, дефолт 1 — поведение не меняется; 2–4 —
параллель). Очередь фиксации с mutex (К2), ограничитель квоты (К4),
футуры + единственный писатель журнала (К5). Ожидание: листовая фаза
ветки ×N быстрее; прогон p5 — примерно вдвое.

**Этап 3 — В4 + В2: спайки и конвейер фаз (1–2 дня).** Спайк —
параллельно спеке; ревью узла A — параллельно декомпозиции узла B.
Требование: возобновляемость (П9) к этому моменту, иначе обрыв длинного
параллельного прогона слишком дорог.

**Этап 4 — В3: параллельные ветки (3+ дня, по потребности).** Только
после стабильных этапов 1–3 и накопленной статистики конфликтов из
очереди фиксации (если откаты в очереди редки — ветки можно). Один
интегратор, ветки — по готовности, корень ждёт всех.

### Ограничения и требования (сводно)

- Движок — единственный владелец состояния; параллелизм только в слое
  вызовов воркеров (футуры), журнал пишет движок.
- Фиксация изменений workspace — строго последовательная (очередь),
  pytest никогда не гоняется параллельно в одном workspace.
- Спеки — резервации поверхности; гейт уникальности — детерминированный.
- Бюджет квоты — глобальный на прогон, не на воркера; при исчерпании
  пул деградирует до последовательного режима, не падает.
- Дефолты сохраняют сегодняшнее поведение (параллелизм = явный флаг).
- Ускорение ограничено критическим путём: цепочка
  «корень → ветка → её интеграция → корень» не параллелится; реалистичная
  цель — ×2–3 на p5, ×3–4 на широких деревьях p4, не «×N воркеров».

## Часть 5. Гибкая настройка воркеров: провайдеры и модели по ролям

Сегодняшнее состояние: одна дверь `llm_backend.ask()` с одним backend'ом
на прогон; модель переопределяется по роли только переменными окружения
(`SPEC_FLOW_DECOMPOSER_MODEL`, `SPEC_FLOW_REVIEWER_MODEL`, ...), провайдер
у всех общий. Этого мало: роли принципиально разные по требованиям.

### Почему роли хотят разных моделей

| Роль | Что важно | Подходящий класс модели |
|---|---|---|
| декомпозер | структурное мышление, следование контракту | сильный instruct (70B+ / sonnet) |
| ревьюер | строгость, знание EARS/конституции | сильный instruct; ДРУГАЯ модель, чем у автора — разные слепые зоны |
| реализатор | код, дисциплина формата | кодовая модель (qwen3-coder, deepseek-coder) |
| исследователь (спайк) | широта знаний | большая общая модель; редкие вызовы — допустима платная по флагу (П8) |
| починка интеграции | чтение чужого кода, точечные правки | кодовая модель с большим контекстом |
| аппрувер/HITL-мост | не модель вовсе (человек/правила) | — |

Принцип «автор ≠ судья»: ревьюер и верификатор-починщик должны по
возможности работать на ДРУГОЙ модели, чем декомпозер и реализатор —
одинаковые модели разделяют слепые зоны, и ревью вырождается в
самопроверку.

### Целевая конфигурация — блок `workers:` в YAML кейса

```yaml
workers:
  defaults:                       # унаследуют все роли
    provider: openrouter-free     # имя профиля провайдера (см. ниже)
    retries: 3
    timeout_s: 600
  decomposer:
    model: "qwen/qwen3-next-80b-a3b-instruct:free"
  reviewer:
    provider: openrouter-free
    model: "meta-llama/llama-3.3-70b-instruct:free"   # ≠ модель автора
  implementer:
    model: "qwen/qwen3-coder:free"
  researcher:
    provider: claude-direct       # редкие спайки — допускается по флагу
    model: haiku
    allow_paid: true              # явный, на одну роль, не глобальный
  repair:                         # починка integrate-гейта
    model: "qwen/qwen3-coder:free"
fallbacks:                        # цепочка на исчерпание/недоступность
  - provider: openrouter-free     # пробовать другой free той же роли
  - provider: claude-direct
    model: haiku
```

Профили провайдеров — отдельный реестр (файл `providers.yaml` уровня
обвязки/плагина), чтобы кейсы не несли транспортных деталей:

```yaml
openrouter-free: {kind: openai, base_url: "http://127.0.0.1:8080/v1",
                  free_only: true, daily_budget: 1000}
claude-direct:   {kind: claude-cli, direct: true}
hermes-gateway:  {kind: openai, base_url: "${BIFROST_URL}"}
```

### Что для этого менять (по слоям)

1. **llm_backend → реестр провайдеров.** `ask(prompt, role=...)` выбирает
   (provider, model) из конфигурации роли; free-гейт и фолбэк становятся
   свойствами ПРОФИЛЯ провайдера, а не глобальными переменными. Бюджет
   (К4 из плана параллелизации) — общий счётчик на профиль.
2. **role_worker._model_for → role_config().** Вместо пары env-переменных
   — слитая конфигурация: defaults кейса ← блок роли ← env-переопределение
   (env остаётся для разовых экспериментов, приоритет выше YAML).
3. **run_cases** читает `workers:` из YAML кейса и передаёт в обвязку;
   `meta.json` пишет фактическую таблицу роль→(провайдер, модель) — какой
   контур реально обслуживал прогон, видно из артефактов.
4. **llm-log**: каждый outcome уже несёт model; добавить provider и
   fallback-цепочку (кто реально ответил после каких отказов).
5. **Дашборд**: колонка «модель» в ленте агентов; сводка стоимости/квоты
   по ролям на вкладке отчёта.

### Ограничения и правила

- Жёсткое правило бесплатного пула НЕ ослабляется: `allow_paid` —
  пер-роль, явный, в YAML кейса на виду; глобального «всё платное» нет.
- Фолбэк-цепочка конечна и журналируется; молчаливых подмен нет.
- Смешение провайдеров не должно ломать воспроизводимость отчёта:
  meta.json фиксирует фактическую карту роль→модель на прогон.
- Профиль провайдера = транспорт + лимиты; модели НЕ зашиваются в
  профиль (роль выбирает модель, профиль — как до неё дотянуться).
- Дефолт без блока `workers:` — сегодняшнее поведение (совместимость).

### Порядок внедрения

1. Реестр провайдеров + role_config в обвязке, env-приоритет (полдня).
2. `workers:` в YAML кейса + meta.json карта роль→модель (полдня).
3. Перевод ревьюера p4/p5 на модель, отличную от декомпозера, замер
   качества ревью (доля содержательных REJECT, доля пропущенных дефектов
   на интеграции) — это первый практический выигрыш гибкости (1 день).
4. provider/fallback в llm-log + дашборд (полдня).

## Часть 6. Память воркеров: memory-провайдеры роли и проекта

Задумка уже описана для агентов Гермеса (`docs/hindsight-guide.md` в
корневом репозитории): Hindsight — agent-memory-провайдер (knowledge
graph: факты + сущности + связи + время; recall четырьмя стратегиями с
rerank; банк = единица полной изоляции, auto-create; API на
`127.0.0.1:8888` в стеке hermes-tools). Переносим ту же модель на
воркеров spec-flow.

### Зачем воркеру память

Сейчас каждый вызов воркера — табула раса: весь контекст собирает
обвязка (карта, контракт, схемы). Это правильно как фундамент, но два
класса знания между вызовами теряются:

1. **Опыт роли** («как я уже ошибался»): ревьюер раз за разом пишет
   одинаковые REJECT-формулировки; реализатор повторяет класс ошибки,
   который в прошлом прогоне чинился три раунда. Память роли превращает
   грабли в директивы: «в этом проекте handler всегда (payload, query)»,
   «тесты не трогают _SCHEMAS».
2. **Знание проекта** (решения и их причины): «выбрали Onfido-стаб,
   потому что...», «таблица payouts принадлежит payout_calculation»,
   «opt-in проверяется перед любым письмом». Сейчас это живёт только в
   спеках; recall по смыслу из них невозможен.

### Двухуровневая схема банков (зеркало схемы Гермеса)

- `specflow-role-<роль>` — память РОЛИ, переживает прогоны: типовые
  дефекты, удачные паттерны, директивы. Маленькая, медленно растёт.
- `specflow-project-<кейс>` — память ПРОЕКТА, живёт с проектом:
  принятые решения (из спайков и закрытых open decisions), владение
  таблицами/маршрутами, причины respec'ов. Наполняется автоматически
  из событий движка (retain на milestone'ах), не воркерами вручную.
- Изоляция банков — штатная (Hindsight bank = полная изоляция);
  cross-bank recall пока нативно нельзя — общие знания дублируются
  retain'ом в оба банка (известное ограничение, roadmap #1589).

### Точки врезки (минимальные)

1. **retain — движок, не воркер.** На событиях: spec PASS (решения из
   § Open decisions), integrate verdict + причина, rework-итог («что
   было не так → как исправили»), вопрос-ответ HITL. Воркер ничего не
   пишет сам — память не засоряется генеративным шумом.
2. **recall — обвязка, перед вызовом.** К промпту роли добавляется блок
   «память» из двух recall'ов (роль + проект, по 3-5 фактов, бюджет
   символов). Та же дисциплина, что с картой: механическая передача,
   модель не «вспоминает», ей показывают.
3. **директивы роли** (жёсткие правила банка) — синхронизируются из
   профиля плагина: profiles/<роль> остаётся источником истины, банк —
   исполняемым кешем.

### Конфигурация — расширение блока `workers:` (Часть 5)

```yaml
workers:
  defaults:
    memory:
      provider: hindsight             # профиль из providers.yaml
      role_bank: "specflow-role-{role}"
      project_bank: "specflow-project-{case}"
      recall_budget_chars: 1500
      recall_top_k: 5
  reviewer:
    memory: {recall_top_k: 8}         # судье — больше прецедентов
  approver:
    memory: off                       # человеку память не подмешиваем
providers.yaml:
  hindsight: {kind: hindsight, base_url: "http://127.0.0.1:8888",
              llm: openrouter-free}   # extract-LLM тоже из free-пула
```

### Ограничения и риски

- **Память — приправа, не фундамент.** Карта репозитория, контракт и
  гейты остаются обязательными; recall не может их заменить (memory
  может молчать или ошибаться — гейты нет).
- **Бюджет**: recall-блок жёстко ограничен (символы и top_k), иначе
  съест контекст слабых моделей.
- **Качество retain**: extract-LLM Hindsight требует внешнюю модель —
  использовать free-пул; на исчерпании retain откладывается в очередь,
  НЕ блокирует прогон.
- **Тестируемость**: в офлайн-тестах memory-провайдер — фейк в памяти
  процесса; харнесс-тесты не зависят от стека hermes-tools.
- **Чистота эксперимента**: включение памяти — флаг кейса; сравнение
  прогонов с памятью/без — отдельный замер (число rework'ов, повторных
  классов ошибок) до того, как делать дефолтом.

### Порядок внедрения

1. Абстракция MemoryProvider в обвязке (retain/recall/директивы) +
   фейк для тестов (полдня).
2. Адаптер Hindsight (REST, банки role/project, авто-создание) +
   retain-хуки на событиях движка (день).
3. recall-блок в промпты ролей с бюджетом (полдня).
4. Замер на p4: два прогона (память off/on), сравнение rework'ов и
   повторных классов дефектов; решение о дефолте по цифрам (день).

## Часть 8. Остановка и продолжение прогона не с нуля

### Зачем
Остановить прогон (перезагрузка машины, конец рабочего дня, пауза на
осмысление), затем продолжить С ТОЙ ЖЕ ТОЧКИ — в том числе с новыми
инъекциями требований, добавленными за время простоя.

### Что уже есть (фундамент)
- Журнал рабочей области: каждый закрытый узел помечается
  (journal_mark / journal_nodes), у движка есть параметр resume —
  реализация листа повторно использует сохранённый артефакт.
- Все артефакты на диске: спеки, код, тесты, trace, llm-log, дерево.
- Требования — артефакты в hitl/requirements/: читаются на каждой
  точке размещения, то есть инъекции «за время простоя» подхватятся
  при продолжении сами.
- Журнал волн (этап 0): атомарные фиксации, срез оборванного хвоста —
  готовый носитель состояния «что уже сделано».

### Чего не хватает (шаги реализации)

1. **Грациозная остановка.**
   - Файл-команда `<run>/hitl/STOP`: проверяется на границах узлов;
     движок дописывает текущий узел, фиксирует журнал, пишет
     `paused.json` (штамп, последний тик, причина) и выходит кодом 0.
   - SIGTERM/SIGINT — то же поведение (обработчик сигнала), чтобы
     перезагрузка системы не отличалась от штатной паузы.
2. **Полнота состояния на диске.**
   - Реализованное дерево писать инкрементально при каждой фиксации
     узла (сейчас tree.json пишется в конце прогона).
   - Счётчики (бюджет вызовов, номера доработок) — в журнал волн,
     при продолжении восстанавливаются оттуда.
3. **Продолжение: `run_cases.py --resume <run-dir>`.**
   - Кейс и флаги наследуются из inputs.json/meta.json прогона.
   - Рабочая область открывается с preserve, journal_nodes даёт
     список готовых узлов → обход пропускает их и продолжает с
     первого незакрытого.
   - Инъекции, добавленные за простой, подхватываются штатно
     (standing requirements читаются на каждом размещении).
4. **Продолжение при параллельности.**
   - Узлы, бывшие «в полёте» на момент остановки, не зафиксированы —
     честно перевыполняются (идемпотентность: лист перезаписывает
     свои файлы; журнал волн не даёт привидеться полузаписи).
5. **Опции.**
   - CLI: `--resume <run-dir>` (продолжить), `--stop <run-dir>`
     (создать STOP-файл живому прогону).
   - Семантика YAML не меняется: «с той же точки» и «с новыми
     инъекциями» — один и тот же механизм, инъекции просто лежат в
     hitl/requirements к моменту продолжения.

### Ограничения (честно)
- Открытый LLM-вызов остановку не переживает — его узел
  перевыполняется (норма, вызовы идемпотентны по артефактам).
- Память (Hindsight) продолжению не мешает: project.mode=resume
  сохраняет решения первой половины прогона.

## П13. Специализация воркера (роль × модель × СПЕЦИАЛЬНОСТЬ) — на подумать/решить

**Идея пользователя (2026-06-13).** Сейчас у воркера два измерения:
роль (декомпозитор/ревьюер/исполнитель/верификатор) и модель (из
workers-блока). Добавить третье — **специальность узла**: в одном
листе исполнитель должен быть «питон-программистом», в другом —
«архитектором / системным дизайнером»; аналогично для других ролей
(ревьюер-безопасник vs ревьюер-перформанс и т.п.).

**Зачем может быть нужно.** Специализированный системный промпт +
подобранная под задачу модель дают лучше результат, чем один
универсальный воркер на все узлы. Узел «спроектировать схему БД» и
узел «написать обработчик HTTP» — разные навыки.

**Как может выглядеть (эскиз, НЕ решение).**
- Узел несёт поле `specialty:` (например `python-impl`,
  `system-design`, `security-review`), проставляется декомпозитором
  при разбиении или эвристикой движка по заголовку/метрикам.
- В workers-блоке — реестр специальностей: каждая задаёт
  `system_suffix` (доп. к SKILL.md) и опц. свой `model` (override
  цепочки роли). Связка становится `(role, specialty) -> (model,
  system)`.
- Карта на дашборде расширяется до роль×специальность→модель.
- compare_runs получает измерение «специальность» для замеров
  «специализация вкл/выкл».

**Открытые вопросы (почему «подумать», а не «делать»).**
1. Кто назначает специальность — декомпозитор (ещё одно поле в его
   JSON, риск мусора) или детерминированная эвристика движка
   (надёжнее, но грубее)? Сверить с правилом «генерация ненадёжна,
   дисциплина — гейтами».
2. Не дублирует ли это уже существующий механизм SKILL.md? Скиллы
   уже задают роль; специальность — это под-скилл. Может, достаточно
   расширить набор скиллов на роль, без нового измерения.
3. Стоит ли усложнение: на p4 один универсальный исполнитель
   справляется. Выгода видна только на узлах с явно разной природой
   (дизайн vs реализация vs миграция). Нужен кейс, где это измеримо
   помогает (через compare_runs), иначе — отклонить как
   преждевременную абстракцию.
4. Бюджет провайдеров: специальность с дорогой моделью на каждом
   профильном узле может выбить квоту — нужна та же дисциплина
   фолбэка/ротации, что и для ролей.

**Решение:** отложено. Брать только если найдётся кейс, где
специализация даёт измеримый выигрыш по compare_runs; иначе
отклонить (правило «не плодить абстракции без измеримой пользы»,
mem: feedback_recommended_path_plus_all_rejected склоняет к проверке
гипотезы, а не слепому внедрению).

## П14. Доска намерений (claim-board) — предотвратить дубль ДО работы, а не мержить после

**Критика пользователя (2026-06-13), справедливая.** Этап 2
(worktree-на-лист + `merge-tree` + слияние по очереди) решает
*физическую* изоляцию, но НЕ устраняет *логический* дубль: две ноды
всё равно могут независимо написать одну и ту же функцию — на это
тратятся вызовы LLM, время и последующий мерж. «Дать столкнуться и
помирить» дороже, чем «не дать столкнуться».

**Идея пользователя.** Перед действием (написать функцию/модуль) нода
сначала смотрит на общую доску намерений: не собирается ли другая нода
сделать то же. Если такое уже создаётся — подождать или взять другую
задачу.

### Прецеденты (что это в индустрии)
| Прецедент | Что берём |
|---|---|
| **Bazel/Buck action cache** — действие объявляет outputs, одинаковые действия по контент-хэшу не выполняются дважды | главное: дедуп ДО запуска по объявленному выходу |
| **2PL / lease-локи (ZooKeeper, etcd)** — claim перед работой, эфемерный узел = «я держу» | claim-токен с владельцем и TTL |
| **STM (read/write sets)** — конфликт по пересечению множеств записи | пересечение «целей» = конфликт |
| **Work-stealing scheduler** — если задача занята, бери соседнюю | при занятой цели — defer на соседний лист |

### Эскиз для spec-flow
- Новый артефакт `<run>/claims.json` (или таблица в общей памяти),
  единый writer через уже существующую `commit_queue` (сериализация
  у нас уже есть).
- **Claim = (target, owner_node, state, ts)**, где `target` —
  объявленный выход: путь модуля `src/<name>.py` и/или список
  публичных функций/маршрутов.
- Протокол листа ПЕРЕД реализацией:
  1. рассчитать свой `target` (из спеки узла: имя модуля + сигнатуры);
  2. под `commit_queue` прочитать доску;
  3. если цель **свободна** → записать claim `in_progress`, работать,
     по завершении → `done` + опубликовать реальный интерфейс в память
     проекта (факты интерфейсов уже есть);
  4. если цель **занята другим in_progress** → не дублировать:
     - либо `depends_on` на владельца и ждать его `done` (затем
       использовать готовый интерфейс),
     - либо взять другой готовый лист (work-stealing), вернуться позже;
  5. если цель **done** → сразу зависимость, без работы.
- **Тай-брейк** при гонке за один target: меньший node-id выигрывает
  claim, второй уходит в `depends_on` (детерминизм, без живоблока).
- **TTL/croak**: claim с дохлым владельцем (лист упал/таймаут —
  предохранители уже есть) освобождается, цель снова доступна.

### Почему это ЛУЧШЕ мержа для дубля
- предотвращает дубль ДО траты LLM-вызовов (мерж тратит и реализацию,
  и разрешение конфликта);
- расширяет уже имеющийся дедуп-гейт движка (`existing_nodes`/
  `depends_on`) с *статического* дерева на *runtime*: поздно
  открытые параллельные листья дерево не видит, доска — видит;
- ортогонален физической страховке (`commit_queue` + git-tx остаются
  для одновременной записи в один файл).

### Открытые вопросы / риски
1. **Точность объявления цели.** `target` объявляет LLM (имя модуля,
   сигнатуры) — риск мусора. Митигация: грубая гранулярность по
   ФАЙЛУ (`src/<name>.py`) надёжнее, чем по функции; имя модуля движок
   и так знает из узла (`fn`), объявление почти детерминированное.
2. **Гранулярность.** Файл — мало ложных конфликтов, но и пропустит
   две функции-дубля в разных файлах. Функция — точнее, но требует
   аккуратного объявления. Начать с файла, при нужде уточнить.
3. **Не дублирует ли это `existing_nodes`-гейт?** Нет: тот срабатывает
   при ДЕКОМПОЗИЦИИ (построении дерева), доска — при ИСПОЛНЕНИИ
   (in-flight). Это две фазы; доска закрывает дыру «дерево уже
   построено, но два листа независимо делают одно».
4. **Стоимость.** Один лишний прочит/запись доски на лист, под уже
   существующим замком — копейки против стоимости дубля+мержа.

### Решение
**Принять как следующий шаг для проблемы ДУБЛЯ** (предпочтительнее
этапа-2 worktree+merge именно для дубликации). Этап-2 (worktree +
merge-tree) остаётся отдельно — для масштабирования физической
изоляции, когда сериализованного общего workspace станет мало. Порядок:
сначала доска намерений (дешёвый, предотвращает дубль), worktree+merge
— позже и только при доказанной необходимости (через compare_runs:
выросло ли число коллизий настолько, что сериализация стала узким
местом).
