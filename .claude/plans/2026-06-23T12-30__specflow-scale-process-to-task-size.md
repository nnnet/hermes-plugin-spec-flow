# Снизить время прогона spec-flow: масштабировать процесс под размер задачи

## Контекст (почему прогон простой задачи идёт >1 часа)

Замер v069 (p6 — крошечный сервис из ~5 файлов): **wall 67 мин**.
Точная причина по логам (`llm-log.jsonl`):

- **~76 вызовов LLM, строго ПОСЛЕДОВАТЕЛЬНО** — wall (67 мин) ≈ сумма латентностей
  (72 мин), перекрытия нет.
- Разбивка вызовов: **implementer 35** (оркестр 4 роли × `creator_ensemble=2` +
  реворки), **reviewer 28** (LLM спец-ревью + impl-ревью + диагноз на КАЖДОМ узле и
  КАЖДОМ реворке), decomposer 11, verifier 2.
- **Латентность вызова**: медиана 25-30 с, среднее 50-90 с (haiku/mimo медленные),
  **хвост до 600 с** на застрявших вызовах (LLM_TIMEOUT 300 с × ретраи).

Корень: движок запускает тяжёлый мульти-агентный конвейер, рассчитанный на СЛОЖНЫЕ
проекты, на тривиальной задаче. **Машинерия «лёгкого пути» уже есть, но выключена
или настроена на максимум качества:**

- `review.tiering: False` (дефолт) → LLM-ревью идёт на каждом узле (детерм-путь
  `_is_simple_node`/`simple_max_loc` в `spec_flow_runner.py:3241` существует, но не
  включён);
- `creator_ensemble: 2` (кейс) → кодер генерит ДВА кандидата на каждый лист
  (`_ensemble_size` в `tests/harness/role_worker.py:681`);
- тиринг #2 (solo) сработал лишь 1 раз — почти все листья классифицированы
  «medium» → полный оркестр из 4 ролей;
- LLM_TIMEOUT 300 с (`tests/harness/llm_backend.py:47`) → один застрявший вызов
  съедает 300-600 с.

Цель: **тривиальная задача ≈ 10-15 мин** (с ~76 вызовов → ~18-25), без потери
качества на СЛОЖНЫХ узлах (масштабируем по сложности узла, не режем глобально).
Все защиты от ложно-зелёного (boot-oracle, delta-гейт, ре-валидация причин) и
параллелизм сохраняются.

## Рычаги (по убыванию эффекта; почти всё — включение/настройка готового)

### 1. Включить review-тиринг для простых листьев (−~15 вызовов reviewer)
`review.tiering` уже реализован (`_is_simple_node`, `spec_flow_runner.py:3241`,
строки 3386+ «lint needs no LLM opinion round — auto-PASS and skip the reviewer»).
Сейчас `tiering: False` в `DEFAULT_REVIEW_POLICY` (`:624`).
- Включить `review.tiering: True` (через `workers`/case-YAML или дефолт), оставить
  детерм-линт (traceability + контракт-гейт) как гейт.
- Простой лист (≤ `simple_max_loc`, single-concern, без open-decisions) проходит
  ревью детерминированно, без LLM спец-ревью и impl-ревью.

### 2. `creator_ensemble` по сложности (−~10 вызовов implementer)
`_ensemble_size()` читает плоское число. Сделать его **функцией сложности узла**:
ensemble=1 для simple/medium, ensemble≥2 только для branch/сложных
(`tests/harness/role_worker.py:681` + прокидывать label узла, как уже делает тиринг
#2). Для тривиальной задачи кодер генерит один кандидат, а не два.

### 3. Шире solo-тиринг (−~30 вызовов: лист 8 вызовов → 1-2)
Почти все листья p6 получили «medium» (→ оркестр), хотя это 20-40-строчные модули.
`_node_complexity_label` (`spec_flow_runner.py`) недооценивает «малость».
- Поднять порог `simple_max_loc` (60 → ~120) **или** добавить «leaf_big» в
  `workers.solo_for_labels`, чтобы малые модули шли solo (один проход кодера с
  безопасным фолбэком в оркестр — фикс a0bf8c0 уже на месте).

### 4. Убить хвост зависших вызовов (−~10-20 мин на стойлах)
LLM_TIMEOUT 300 с → max-вызов 600 с. Снизить до ~120 с (через `workers.timeout`),
плюс уже есть 5xx/timeout breaker и fast-failover. Застрявший вызов быстро уходит в
фолбэк, а не морозит прогон.

### 5. Кап доктор-петель на узел — ОЦЕНЕНО: правка не нужна
v069 — 22 лечения, но это СУММА по ~9 узлам, не петля одного узла. Per-node капы уже
корректны и сходятся в debt: `max_rework: 2` (review) и `integrate_max_rework: 2`
(`spec_flow_runner.py:2679`, debt-путь `:3465`). Тупое снижение рискует недолечить
реальный дефект (регресс heal-миссии). Настоящее сокращение нагрузки на доктора даёт
#1 (review-тиринг): меньше узлов отправляется в spec-review → меньше FAIL → меньше
diagnose/rework естественно. Числа НЕ режем.

## Что НЕ трогаем

- Параллелизм — НИКОГДА не выключать (правило); рычаги его не отключают.
- Защиты от ложно-зелёного: boot-oracle, `_late_req_delta_gate`,
  `_prune_stale_causes` — остаются. Лёгкий путь применяется только к ПРОСТЫМ узлам;
  сложные сохраняют полную машинерию.

## Охват: ДВИЖОК ПО УМОЛЧАНИЮ (все малые проекты быстрые), все 5 рычагов

Меняем ДЕФОЛТЫ движка (масштабирование по сложности узла — встроенное поведение),
а не только кейс p6. Любой малый проект быстрый из коробки; сложные узлы сохраняют
полную машинерию. Риск задеть другие кейсы (p4/p5) закрываем тем, что лёгкий путь
включается ТОЛЬКО для узлов, которые детерминированно простые (метрики), и полным
прогоном офлайн-набора + замером p4/p5 после изменений.
