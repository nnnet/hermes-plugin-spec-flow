# План проверки: любой кейс → готовый к использованию продукт

**Цель.** Любой кейс из `tests/scenarios/*.yaml`, поданный в плагин, должен на
выходе давать **готовый к использованию продукт**, а не только артефакты
оркестрации. В идеале продукт умеет **самосовершенствоваться**: сам замечает,
что устарел или сломался, и сам доводит себя до зелёного через ленту ревизии.

**Сегодняшняя база (уже проверено, 132 теста):** гейты на настоящих данных,
дерево по настоящим порогам, оба вида дрейфа, циклы критики, ревизия с
переоткрытием поддерева, лестница глубины `spec→scaffold→verify→execute`,
механика передачи работы агенту, аудит R1–R8, покрытие 9/9 скиллов и 6/6
профилей (тест `test_case_coverage.py`).

**Разрыв.** На `execute` код пишет автономная заглушка — продукт формально
«зелёный», но функционально пустой. Проверка «готовый продукт» требует трёх
недостающих слоёв: настоящий исполнитель, продуктовая приёмка, замкнутый цикл
самосовершенствования.

---

## Этап 1 — приёмка продукта внутри кейса (схема `acceptance`)

Кейс должен сам говорить, что значит «продукт готов». Расширить схему кейса:

```yaml
acceptance:
  entrypoint: "python3 -m app"            # как продукт стартует
  smoke:                                   # продукт жив
    - "GET /health -> 200"
  e2e:                                     # сценарий пользователя от и до
    - "создать листинг -> найти поиском -> оформить заказ -> счёт в центах"
  metrics:                                 # цель из target -> проверяемые пороги
    - "p95 checkout < 500ms на 100 запросах"
contracts_live: true                       # contract_check против РАБОТАЮЩЕГО API
```

Шаги:
1. Добавить секцию `acceptance` во все 4 кейса (из их `target`).
2. Написать `tests/harness/product_check.py`: поднимает продукт из воркспейса
   (`entrypoint`), гонит smoke/e2e/metrics, пишет `PRODUCT-RESULTS.md`.
3. Критерий этапа: прогон с заглушкой-исполнителем даёт честный вердикт
   **НЕ ГОТОВ** (smoke падает) — приёмка не самообманывается.

## Этап 2 — настоящий исполнитель (агент пишет работающий код)

1. Адаптер `implementer` на живом агенте (Hermes-воркер или Claude Agent SDK):
   вход — спека листа (в ней уже есть метрики, решённые развилки, контракт,
   эпизоды), выход — рабочий код + тесты в воркспейс.
2. Леса уже готовы: инжекция через `agents=`, контракт сверяется настоящим
   валидатором, юнит-тесты гоняются на `verify+`.
3. Критерий этапа: на одном кейсе (начать с p2 — самый маленький продукт)
   все юнит-тесты листьев зелёные и `contract_check` чистый **на коде агента**.

## Этап 3 — продуктовый уровень глубины (`depth=product`, пятый)

1. Новый уровень лестницы: `spec < scaffold < verify < execute < product`.
2. На `product` после `execute`: собрать продукт → запустить → прогнать
   `acceptance` кейса → `PRODUCT-RESULTS.md` с вердиктом ГОТОВ/НЕ ГОТОВ
   и списком непройденного.
3. `contracts_live`: `contract_check` против работающего API, не манифеста.
4. Критерий этапа: `run_cases.py --depth product --case p2` даёт **ГОТОВ**;
   в `SUMMARY.md` появляется строка «продукт: ✅ пригоден к использованию».

## Этап 4 — самосовершенствование (замкнутый цикл ревизии)

Лента ревизии уже умеет: курок (`research_trigger_check`) → находка → respec →
переоткрытие поддерева → перегон листьев. Замкнуть её на продукт:

1. Источники сигналов вместо YAML-фикстуры: ошибки `acceptance`, ошибки
   тестов (`m_test_errors` — курок уже есть), деградация метрик, «смена
   правил среды» (фикстура изменения: правка контракта/закона/комиссии).
2. Цикл: сигнал → ревизия → respec → re-derive → execute листьев → повторная
   приёмка. Повторять до зелёного или до стоп-условия.
3. Стоп-условия (анти-зацикливание, уже заложены в respec-gate): бюджет
   переоткрытий, порог доказательств, ручное подтверждение при большом
   радиусе поражения.
4. **Главный тест самосовершенствования** (`test_self_improvement.py`):
   - прогнать кейс до ГОТОВ;
   - сломать среду (подменить контракт-фикстуру/правило — как ревизия PSP в p4);
   - убедиться: плагин **сам** (без правки кейса) ловит сигнал, переоткрывает
     задетое поддерево, перегоняет листья и возвращает приёмку в зелёное
     состояние за ≤ N итераций;
   - аудит финального трейса: R1–R8 без ошибок, в трейсе видны оба уровня
     ревизии (spike + continuous).

## Этап 5 — критерии приёмки всей проверки (чек-лист ревизионера)

| # | Проверка | Чем доказывается |
|--:|---|---|
| 1 | размытая постановка не строится | `policy-report.md`: block → pass |
| 2 | дерево целей построено и обосновано | `workflow.md` + `specs/*` (метрики, причины) |
| 3 | каждый лист реализован настоящим агентом | `src/*` нетривиален, юнит-тесты зелёные |
| 4 | контракты совпадают, дрейфы разобраны | `contract_check` чист, эпизоды в трейсе |
| 5 | продукт запускается и делает свою работу | `PRODUCT-RESULTS.md`: smoke+e2e+metrics ✅ |
| 6 | продукт самовосстанавливается после смены среды | тест этапа 4 зелёный |
| 7 | метод не нарушен | аудит R1–R8 в `report.md` без ошибок |

## Порядок и объём

1. Этап 1 (схема + product_check + честный НЕ ГОТОВ) — мал, без внешних зависимостей.
2. Этап 3 (уровень `product`) — мал, строится на этапе 1.
3. Этап 2 (живой исполнитель) — требует агента (Hermes-воркер или SDK-ключ); начать с p2.
4. Этап 4 (самосовершенствование) — после 1–3; главный тест ценности.
