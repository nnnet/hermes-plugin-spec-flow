# Fast-fail mimo — почему v091 шёл 61 мин и как ускорить до ~15

> Реализовано: коммит `d6b82cd` (+ резолвер-фикс `b06277d`). Этот файл —
> проектная версия плана (был в `~/.claude/plans/buzzing-shimmying-charm.md`).

## Контекст / диагноз (llm-log v091, 61 мин)
- **67 LLM-вызовов, 25 (37%) = `xiaomimimo/mimo-v2.5` → HTTP 504.** Шлюз Bifrost
  держит каждый 504 ~120с. **25 × ~120с ≈ 50 мин** = и есть час.
- Per-call таймаут был **420с** (`SPEC_FLOW_LLM_TIMEOUT`), p6 не переопределял.
- Брейкер ретайрил mimo после **2 ПОДРЯД** 5xx, но mimo **мерцал** (200/504/...)
  → счётчик сбрасывался → за прогон открылся лишь 2 раза на 25 фейлов.
- **Дашборд врал:** реальных `quota_wait` = 0; классификатор простоев сваливал
  `error_round` (от 504) в бакет «ожидание квоты» → «42 мин квоты» = на деле
  mimo-504-таймауты.
- «Реализация 64 мин» — тоже в основном ожидание дохлого mimo, не генерация
  (реальные генерации ~16с).

## Фикс (внедрён, 3 связанные правки)
1. **Брейкер: `timeout` → ретайр после 1** (`tests/harness/llm_backend.py`,
   `_reason == "timeout" → _retire_at = 1`, иначе `model_breaker_5xx`). Висящий
   шлюз не лечится в прогоне — платить второй раз незачем.
2. **p6 `workers.timeout: 75`** (`tests/scenarios/p6_micro_notes.yaml`). Реальные
   вызовы ~16с; дохлый mimo обрывается как client-timeout на 75с (ДО шлюзового
   504 на 120с) → классифицируется `timeout` → ретайр после 1.
3. **Честный лейбл дашборда** (`tests/lib/live_dashboard.py`): `error_round`
   (5xx/таймаут провайдера) разведён с `quota_wait` в бакет «ожидание провайдера
   (5xx/таймаут)».

Связка 1+2 — ключ: низкий таймаут превращает медленный шлюзовый 504 в быстрый
client-timeout, который брейкер ретайрит сразу.
