"Разобрался в архитектуре. Ключевая идея, как пишет автор:" **не строить агента с нуля, а «затюнить» готовое ядро Hermes** . Поэтому «имплементация в Hermes» — это не написание agent loop, а обвязка вокруг готового `hermes` CLI. Вот из чего она конкретно складывается.

#### Базовый принцип

Hermes сам владеет циклом агента, вызовом инструментов и рассуждением. Свой код отвечает только за жизненный цикл задачи, промпт, изоляцию и пост-обработку ссылок. Запуск — это subprocess `hermes -z PROMPT` в one-shot режиме (одна сессия на задачу).

#### 1. Установка и запуск ядра

```bash
pip install hermes-agent hermes --version
```

В `hermes_agent.py` Hermes вызывается как подпроцесс с собственным изолированным `HERMES_HOME` (чтобы не подтягивался пользовательский `~/.hermes` с чужими MCP/skills/rules) и с флагом `"--ignore-rules"`, чтобы Hermes не инжектил свои" `AGENTS.md` / `SOUL.md` — твой промпт становится единственным источником поведения.

#### 2. Изоляция через config.template.yaml

"Это сердце «тюнинга». В шаблоне конфига:"

- `platform_toolsets.cli` сводится к `"[bitgn-ecom, skills]"` — то есть только твой MCP-сервер и механизм скиллов;
- все остальные встроенные тулсеты (terminal, file, web, browser, code_execution, vision, memory, todo, messaging и т.д.) переносятся в `disabled_toolsets` ;
- `auxiliary` LLM-провайдеры обнуляются, чтобы агент не уходил в другие модели;
- `"model_catalog.enabled: false"` .

Конфиг рендерится в `config.yaml` в рантайме ( `_render_hermes_config` ), чтобы в репозитории не было машинно-зависимых абсолютных путей.

#### 3. Единственный канал — свой MCP-сервер

`ecom_mcp_server.py` — это `FastMCP("bitgn-ecom")` stdio-сервер. Он оборачивает gRPC-API виртуальной машины в MCP-инструменты ( `ecom_tree`, `ecom_read`, `ecom_exec`, и т.д.). Hermes пробрасывает в подпроцесс конфигурацию через переменные окружения (" `VAULT_HARNESS_URL`, `VAULT_MCP_REFS`, `VAULT_MCP_LOG` ). Это вся точка контакта модели с внешним миром.

#### 4. Конструкция промпта

Промпт для `hermes -z` "собирается строго по порядку: preamble (рамка мира + правила инструментов) → instructions (операционный playbook: security fast-path, правила счёта, выбор Outcome, протокол grounding refs) →" `<bootstrap-output>` (предварительный read-only снимок VM) → инструкция задачи.

#### 5. Дисциплина grounding-references

"Самый сильный рычаг точности в их экспериментах. Реализуется на уровне MCP:"

- `ecom_read(path)` — читает файл **и трекает** путь как grounding ref;
- `ecom_read_silent(path)` — читает **без** трекинга (для файлов, которые смотришь только для вычислений/исключений).

Сервер сбрасывает набор в JSON ( `VAULT_MCP_REFS` ); после выхода Hermes `hermes_agent.py` читает его, санитизирует и передаёт в `vm.answer(...)` . Доверие собственным `ecom_read` модели вместо цитирования всего, что тронул сервер, дало +22pp.

#### 6. Роутинг моделей

Дешёвая модель по умолчанию, дорогая — только на «тяжёлый кластер» (счёт SKU, доступность, fraud). Решение принимает регулярка по тексту инструкции ( `_PRO_ROUTE_RE` в `main.py` ), без отдельного LLM-вызова. Роутинг по типу задачи, не по `task_id` — чтобы не оверфититься.

Отлично, теперь по обоим вопросам есть фактура. Отвечаю по частям.

#### 1. _route_model / регулярка — что, где, как

**Что это.** "Это маршрутизатор моделей: дешёвая функция, которая по тексту инструкции задачи решает, какой модели её отдать — дешёвой (Flash, по умолчанию) или дорогой (Pro). Никакого отдельного LLM-вызова для классификации нет — это просто регулярное выражение по строке инструкции."

**Где живёт.** В `agent/main.py`, в функции" `_route_model`, использует константу-регекс" `_PRO_ROUTE_RE` . Вызывается в цикле прогона прямо перед `run_agent`:

**Как работает.** "Логика примерно такая (реконструкция по описанию из ARCHITECTURE.md §7 — точные формулировки в исходнике, но механизм именно этот):"

```python
"import re _PRO_ROUTE_RE = re.compile( r\"(how many|resolve this product request|in stock|\" r\"units? available|does .+ exist|impossible travel|\" r\"risk ops|fraud|chargeback)\", re.IGNORECASE, ) def _route_model(instruction: str, default_model: str) -> str: if _PRO_ROUTE_RE.search(instruction): return PRO_MODEL_ID # deepseek/deepseek-v4-pro return default_model # deepseek/deepseek-v4-flash"
```

"Несколько важных деталей из устройства:"

- Дешёвая модель ( `MODEL_ID` ") тянет основную массу — шопинг, чекаут, саппорт, OCR. На «тяжёлом кластере» (счёт/резолв SKU, наличие на складе, fraud-архивы) она упирается в потолок: игнорирует протокол «трекать только квалифицирующие SKU» и ошибается в подсчётах. Туда и уходит Pro."
- Маршрутизация **по типу задачи** (через паттерн в тексте), а **не по `task_id`** . Это намеренно — чтобы не оверфититься на конкретный сплит бенчмарка. Если бы роутили по id задач, это была бы подгонка под датасет.
- Примерно четверть задач уходит вверх, поэтому стоимость прогона лежит между «всё дешёвое» и «всё дорогое».
- Каждое решение пишется в лог как событие `model_routed`, чтобы после прогона можно было проверить, что и куда ушло."

"Где это крутить: README прямо говорит — меняешь дефолтную/сильную модель в" `MODEL_ID` / `PRO_MODEL_ID` в `.env`, а какие задачи идут на сильную — правишь" `_PRO_ROUTE_RE` / `_route_model` в `agent/main.py` . Python трогать не обязательно, кроме самой регулярки.

#### 2. delegation — что за тулсет, откуда и как работает

**Откуда.** Это **встроенный тулсет самого Hermes** (NousResearch/hermes-agent), не что-то из этого репозитория. В Hermes есть фиксированный набор тулсетов; в их `AGENTS.md` "перечислены ключи:" `browser, clarify, code_execution, cronjob, debugging, delegation, file, memory, messaging, skills, terminal, todo, vision, web` и др. `delegation` — один из них.

**Что он делает.** Даёт агенту инструмент `delegate_task`, который порождает дочерних суб-агентов. Механика по докам Hermes:"

- `delegate_task` спавнит дочерний `AIAgent` с **изолированным контекстом**, собственной терминальной сессией и урезанным набором тулсетов. У ребёнка свежий диалог — он ничего не знает об истории родителя; родитель обязан явно передать всё нужное через параметры" `goal` и `context` .
- Работает **синхронно** ": родитель ждёт итоговое summary ребёнка, и только это summary попадает в контекст родителя (промежуточные вызовы инструментов контекст не засоряют — отсюда «zero-context-cost» подзадачи)."
- "Два режима: одиночный (" `goal` ) и батч-параллельный ( `"tasks: [...]"` ), параллелизм ограничен `delegation.max_concurrent_children` (по умолчанию 3).
- По умолчанию делегирование «плоское» ( `"max_spawn_depth: 1"` "): родитель спавнит листья, которые сами делегировать не могут. Вложенность опциональна и только через" `role="orchestrator"` .
- Настройки под ключом `"delegation:"` в `config.yaml`: `model` / `provider` (можно дать детям другую модель), `max_concurrent_children`, `max_spawn_depth`, `child_timeout_seconds`, `orchestrator_enabled`, `max_iterations` и т.д.

**Почему он в этом репо в `disabled_toolsets` .** Здесь архитектура намеренно сводит агента к **одному каналу** — MCP-серверу `bitgn-ecom` . Всё, что даёт модели другой способ «что-то сделать» (терминал, файлы, web, code_execution и в том числе `delegation` "), выключается. Причины две:"

- Безопасность/изоляция — модель не должна порождать суб-агентов с собственными сессиями и тулсетами в обход единственного разрешённого канала.
- Чистота скоринга — лишние способности позволяют модели «жульничать» инструментами, которые на самом деле не влияют на VM задачи, и портят дисциплину grounding-ссылок.

То есть `delegation` тут — это не их код, а возможность Hermes, которую они **сознательно отключили**, оставив включёнными только" `skills` и `bitgn-ecom` .

Вытащил исходники. Отвечаю по факту — с реальным кодом из репозитория Hermes ( `NousResearch/hermes-agent` ).

#### Где лежат

Каждый инструмент — это отдельный файл-модуль в каталоге `tools/`, который сам себя регистрирует при импорте:"

- `delegation` → `tools/delegate_tool.py` (инструмент `delegate_task`, ~880 строк)"
- `clarify` → `tools/clarify_tool.py` (инструмент `clarify` ), плюс хелпер для мессенджеров `tools/clarify_gateway.py`

Сами «тулсеты» (группы инструментов) объявлены одним словарём `TOOLSETS` в `toolsets.py`, а базовый бандл, который наследует большинство платформ, — это список" `_HERMES_CORE_TOOLS` там же. И `clarify`, и" `delegate_task` входят в этот core-бандл.

#### Общий механизм: как инструмент вообще «появляется»

У всех инструментов Hermes один паттерн. В конце файла модуля вызывается `registry.register(...)` "— это и есть «подключение к движку»:"

```python
"from tools.registry import registry registry.register( name=\"delegate_task\", # имя в API-схеме toolset=\"delegation\", # к какому тулсету относится schema=DELEGATE_TASK_SCHEMA, # OpenAI function-calling схема handler=lambda args, **kw: delegate_task(...), # что выполняется check_fn=check_delegate_requirements, # доступен ли (True/False) emoji=\"🔀\", )"
```

При импорте `model_tools.py` запускается `discover_builtin_tools()` (из `tools/registry.py` ), которая проходит по `tools/*.py`, AST-проверкой находит файлы с вызовом" `registry.register()` на верхнем уровне и импортирует их. Новый файл подхватывается автоматически — ручного списка нет.

"Важная деталь именно для этих двух:" `delegate_task`, `clarify`, `todo`, `memory`, `session_search` — это **agent-loop-перехватываемые** инструменты. Им нужен доступ к состоянию текущей сессии, поэтому `run_agent.py` перехватывает их вызов **до** обычного `registry.dispatch()` . В реестре их схемы лежат, но если перехват обойти, `dispatch()` вернёт fallback-ошибку.

#### delegation (delegate_task) — как работает

**Что делает.** Порождает дочерних агентов ( `AIAgent` ) с изолированным контекстом, своей терминальной сессией и урезанным набором тулсетов. В контекст родителя возвращается только финальное summary — промежуточные вызовы инструментов ребёнка туда не попадают.

**"Ключевые константы из файла:"**

```python
"DELEGATE_BLOCKED_TOOLS = frozenset([ \"delegate_task\", # нет рекурсивного делегирования \"clarify\", # нет взаимодействия с пользователем \"memory\", # нет записи в общий MEMORY.md \"send_message\", # нет кросс-платформенных side-effect'ов \"execute_code\", # дети должны рассуждать пошагово, а не писать скрипты ]) MAX_CONCURRENT_CHILDREN = 3 MAX_DEPTH = 2 # родитель(0) → ребёнок(1) → внук отклоняется DEFAULT_MAX_ITERATIONS = 50 DEFAULT_TOOLSETS = [\"terminal\", \"file\", \"web\"]"
```

**Как вызывается моделью.** "Через function-calling. Два режима:"

```python
"# одиночный delegate_task(goal=\"...\", context=\"...\", toolsets=[\"terminal\",\"file\"]) # батч (параллельно, до 3 задач) delegate_task(tasks=[{\"goal\": \"...\", \"context\": \"...\"}, {\"goal\": \"...\"}])"
```

**Что происходит внутри `delegate_task()`:**

- "Проверка глубины: если" `_delegate_depth >= MAX_DEPTH` → ошибка, внуки запрещены.
- `_load_config()` читает секцию `"delegation:"` из конфига; `_resolve_delegation_credentials()` решает, на какой модели/провайдере запускать детей (можно отправить их на другой `provider:model`, иначе наследуют родителя)."
- Нормализация в список задач (батч режется до `MAX_CONCURRENT_CHILDREN` ).
- `_build_child_agent()` для каждой задачи на главном потоке (потокобезопасно) строит `AIAgent` с `enabled_toolsets=child_toolsets` ". Важно: тулсеты ребёнка" **пересекаются** с тулсетами родителя (ребёнок не может получить то, чего нет у родителя) и прогоняются через `_strip_blocked_tools()` . Системный промпт ребёнка собирает `_build_child_system_prompt(goal, context)` — это focused-промпт «ты сабагент, сделай X, верни краткое summary».
- "Запуск: один ребёнок — напрямую" `_run_single_child()` ; несколько — через `ThreadPoolExecutor(max_workers=3)`, результаты собираются по мере готовности и сортируются по" `task_index` .
- Возврат — JSON с массивом `results` "(по записи на задачу:" `status`, `summary`, `api_calls`, `duration_seconds`, `tokens`, `tool_trace`, `exit_reason` ).

**Синхронность и прерывания.** Родитель блокируется до завершения детей; дети регистрируются в `parent_agent._active_children`, поэтому прерывание родителя гасит активных детей."

**"Из чего состоит файл (карта функций):"**

| | |
| `delegate_task(...)` | |
| `_build_child_agent(...)` | Конструирует дочерний `AIAgent` (тулсеты, креды, промпт) |
| `_run_single_child(...)` | |
| `_build_child_system_prompt(...)` | |
| `_strip_blocked_tools(...)` | Вырезает `delegation/clarify/memory/code_execution` |
| `_build_child_progress_callback(...)` | |
| `_resolve_delegation_credentials(...)` | Резолв `provider:model` для детей |
| `_load_config()` | Читает секцию `"delegation:"` |
| `DELEGATE_TASK_SCHEMA` | OpenAI-схема (описание, параметры `goal/context/toolsets/tasks/...` ) |
| `registry.register(...)` | Регистрация в реестре под тулсетом `delegation` |

#### clarify — как работает

**Что делает.** "Задаёт пользователю вопрос, когда нужно уточнение/решение, и приостанавливает цикл до ответа. Два режима (по официальному справочнику): множественный выбор — до 4 вариантов, плюс автоматический 5-й вариант «Other» для своего ответа; и открытый вопрос."

**"Как вызывается:"**

```python
"clarify(question=\"Деплоить в prod или staging?\", choices=[\"prod\", \"staging\"]) # или открытый вопрос clarify(question=\"Какой домен использовать?\")"
```

**Как работает по платформам.** "Это интерактивный инструмент, поэтому он:"

- форсит **последовательное** исполнение (в отличие от остальных tool-call'ов, которые Hermes гоняет параллельно через ThreadPoolExecutor) — иначе агент мог бы продолжить до получения ответа;
- перехватывается в `run_agent.py` как agent-loop-tool (нужен доступ к сессии/каналу);
- в мессенджерах ответ ловится через `tools/clarify_gateway.py` ( `get_pending_for_session()` ), который различает choice-based и text-based clarify по флагу `awaiting_text` . В CLI варианты рисуются как меню, в Telegram — кнопками.

#### 1. Spec-driven в Hermes — это скиллы, а не MCP-серверы

Все инструменты из твоего документа (spec-kit, spec-coding-mcp, spec-generator) — это **внешние MCP-серверы / CLI**, которые навязывают структуру снаружи. Соответствующий бандл — `software-development`, и он почти 1:1 кроет фазы spec-kit:"

| | | |
| `subagent-driven-development` | Исполняет план, диспатча свежего сабагента на каждую задачу с двухстадийным ревью — сначала на соответствие спеке, потом на качество кода. GitHub GitHub | `/speckit.tasks` + `/speckit.implement` |
| `test-driven-development` | Принуждает цикл RED-GREEN-REFACTOR, тесты до кода. Nousresearch Nousresearch | |

| | Пишет markdown-план в .hermes/plans/ без исполнения. Nousresearch Nousresearch | |

"Ключевое отличие от твоего списка: spec-kit и прочие — это сервера, которые надо подключать; в Hermes структура уже встроена как инструкции, исполняемые тем же циклом агента (это ровно тот же принцип «тюнить, а не строить», что был в ecom-agent). #### 2. Полный цикл разработки до завершения проекта

Собирается из этих скиллов плюс нативных тулов `clarify` / `todo` / `delegate_task` / `terminal` ". Канонический поток (он буквально прописан в самих скиллах):"

- **Уточнение задач.** На входе агент гонит неоднозначности через `clarify` (помнишь — форсит последовательность и ждёт ответа юзера). Для размытых идей — скилл «throwaway experiments to validate an idea before build».
- **Спека/план.** `writing-plans` "пишет markdown-план: линейный список задач по 2–5 мин с путями, кодом и шагами проверки. Принцип: хороший план делает реализацию очевидной; если кому-то приходится гадать — план неполон." GitHub GitHub
- **Исполнение.** `subagent-driven-development` читает план ОДИН раз, извлекает все задачи разом, создаёт todo-лист со всеми задачами, и дальше диспатчит свежего сабагента на задачу. GitHub GitHub
- **Тесты внутри задачи (TDD).** Каждая задача в плане — это цикл write-test → run (ожидание FAIL) → minimal impl → run (ожидание PASS). Это зашито в шаблон `writing-plans` .
- **Двухстадийное ревью + фиксы.** "После реализации задачи — два ревью-сабагента: сначала проверка соответствия спеке (все требования реализованы? пути совпадают? сигнатуры? нет ли scope creep?) с выводом PASS или списком расхождений; если расхождения найдены — фиксим и перезапускаем spec-ревью, продолжаем только когда соответствует спеке. Затем — ревью качества кода." GitHub GitHub
- **Обработка ошибок по ходу.** "Если сабагент натыкается на баги во время реализации — он сообщает родителю, тот решает: перезапустить задачу, скорректировать план или делегировать фикс." GitHub GitHub
- **Pre-commit gate.** `requesting-code-review` "перед коммитом: после имплементации фичи/багфикса, перед git commit/push, или когда юзер говорит \"commit/ship/done/verify\"; запускается после задач с 2+ правками файлов." Nousresearch Nousresearch
- **Финальная верификация и завершение.** `verification-before-completion` гоняет свежие проверочные команды, частые коммиты. Прогресс трекается статусами в `todo` ; цикл крутится, пока todo-лист не закрыт.

"То есть «до полного завершения» обеспечивается не одним циклом, а вложенными петлями: внешняя — по задачам todo-листа; внутренняя — TDD + spec-review-fix-re-review на каждой задаче."

#### 3. Что если дерево спецификаций глубокое

Здесь три вещи сходятся, и это важно понимать, чтобы не упереться в стену.

**Сам дизайн скилла намеренно НЕ строит глубокое дерево.** План — это **плоский линейный список** "мелких задач, а не рекурсивная иерархия. План читается один раз и разворачивается в todo-лист, после чего каждая задача исполняется свежим сабагентом — то есть по умолчанию это глубина 1 (родитель → лист). Это сделано осознанно: плоская декомпозиция + изолированный контекст на задачу держит контекст родителя чистым (возвращаются только summary)." GitHub GitHub

**Если задачи сами требуют под-декомпозиции — упрёшься в потолок делегирования.** "Как разбирали в прошлый раз: вложенность включается только через" `role="orchestrator"` + поднятый `max_spawn_depth`, и она зажата в диапазон" **1–3** ". Глубже трёх уровней уйти нельзя в принципе. И стоимость растёт мультипликативно: при depth 3 и width 3 дерево разрастается до 27 одновременных leaf-агентов. Плюс — чем глубже и длиннее, тем раньше срабатывает сжатие контекста (preflight на 50%, gateway-автосжатие на 85%) с потерей деталей."

**Для реально больших/глубоких проектов graduate на Kanban, а не углубляй дерево делегирования.** "Это прямой замысел Hermes: Kanban — устойчивая доска задач, позволяющая нескольким агентам работать без хрупких in-process роёв сабагентов; каждый воркер — полноценный OS-процесс со своей идентичностью. Критерий переключения тоже задокументирован: delegate_task — когда родителю нужен короткий ответ-рассуждение перед продолжением; Kanban — когда работа пересекает границы агентов, должна пережить перезапуски, может потребовать человека или быть подхвачена другой ролью. Зависимости между задачами на доске выражаются через" `kanban_link` / `kanban_block` / `kanban_unblock` и статусы (triage → todo → ready → running → blocked → done → archived) — это даёт **неограниченный по размеру DAG задач**, persisted в SQLite, который обходит лимит глубины делегирования, потому что воркеры — отдельные процессы, а не вложенные in-context сабагенты." #### Ключевое решение: рекурсия живёт на доске, а не в контексте

Скилл `spec-flow-decompose` написан так, что **каждый узел дерева — это отдельная Kanban-задача → отдельный OS-процесс** ". Декомпозер обрабатывает ровно один узел: читает утверждённую спеку родителя, пишет спеку своего уровня, проходит гейт, и либо разворачивает следующий уровень (branch), либо эмитит задачи реализации (leaf). Дальше диспетчер сам спавнит свежего декомпозера на каждого ребёнка. Поэтому глубина дерева" **неограничена** — лимит `max_spawn_depth ≤ 3` из `delegate_task` здесь не действует, потому что это не вложенные субагенты, а задачи на доске.

#### Как реализованы два твоих требования

**Top-Down с жёсткими уровнями.** Узел сам решает, лист он или ветка, через детерминированный `leaf_check` "из плагина (модули ≤1, задачи ≤5, интерфейсы ≤2, нет открытых решений, критерии тестируемы) — это и есть «жёсткие контролируемые уровни», а не декомпозиция на глаз. Никакого глобального «разбей до конца»: один прогон = один уровень вниз (правило в Anti-temptation)."

**«Каждый следующий уровень — строгое следствие предыдущего».** "Это зашито двумя механизмами: (1) поле" `Traces-to` "в спеке — любой in-scope пункт без трассировки к требованию родителя удаляется как scope creep; (2) сам DAG: цепочка" `spec → review → expand → children` делает следующий уровень буквально рёберным следствием **прошедшего** ревью.

Хороший вопрос — он бьёт ровно в шов методологии. Чистый top-down SDD предполагает, что спека «застывает» и каждый уровень — следствие предыдущего, то есть информация течёт **вниз** . Разберу по двум случаям, потом отвечу на четыре конкретных вопроса.

#### Случай A: ресёрч только информирует (не меняет направление)

"Если исследование питает соседнюю реализацию, но не отменяет вышестоящих решений — оно ложится в DAG идеально, как обычная задача-родитель. Это и есть штатный паттерн Kanban: research triage — параллельные ресёрчеры + аналитик + writer, с человеком в цикле. Спеки не меняются — ресёрч просто заполнил пробел в одном узле. Nousresearch Nousresearch

#### Случай B: выводы могут изменить проект (информация вверх)

Вот тут пайплайн ломается, и это нельзя замолчать. Находка вида «API, который мы заложили на L2, не поддерживает X» инвалидирует не лист, а решение **выше по дереву** . Чистый «строгое следствие предыдущего» этого не предусматривает.

Решается это тем же принципом, что уже есть в `drift-gate`, только обобщённым:" **никогда не правим следствие молча — сначала правим причину (спеку), потом передеривируем** ". То есть находка с upstream-эффектом обязана:"

- заблокировать зависимые задачи ( `kanban_block` ), а не дать им тихо продолжиться;
- создать `respec` "-задачу на тот узел уровня N, чьё решение опровергнуто;"
- прогнать новую спеку через тот же `spec-gate` (всё ещё трассируется к L1/конституции?);
- передеривировать поддерево под N.

#### Как развивается реализация

"Ключевое преимущество DAG: он" **локализует радиус поражения** ". Когда respec приземляется на узел N:"

- инвалидируется только то, что строго ниже N (поддерево N) — DAG точно показывает, что именно;
- затронутые задачи уходят в `block → unblock → re-run` против новой спеки; могут появиться новые листья, а часть старых — архивироваться;
- интеграционные узлы пересобирают только затронутое поддерево;
- **всё, что не зависело от изменённого решения, остаётся как есть** — не рестарт проекта, а инкрементальная пересборка.

То есть эволюция = «respec на N → инвалидация поддерева(N) → параллельная передеривация → реинтеграция», при сохранении завершённой работы в незатронутых ветках.
