## Top findings

1. **[P7/high]** `spec_flow_runner.py:2288` — Verdict string in `_judge_leaf`'s `emit()` is logically inverted (`"PASS" if verdict == "fail" else "FAIL"`), recording every judge-rejection as PASS in the event trail and making the gate appear GREEN to all downstream consumers; simultaneously the failure carries no attributable FAIL verdict in the ledger. (also at :2288 P4 attribution)

2. **[P7/high]** `spec_flow_runner.py:7947` — `render_report` unconditionally emits `✅ (L0 integrate done)` regardless of `root_red` or actual READY/NOT-READY verdict, injecting a green checkmark into the head of every report and directly enabling substring mis-classification.

3. **[P7/high]** `spec_flow_runner.py:7511` — When an entrypoint exits cleanly, every smoke/e2e/metrics check is bulk-recorded PASS with `'entrypoint ran cleanly'` without evaluating individual check text; a single boolean collapses N declared gates into one signal, fabricating N-1 unearned PASSes.

4. **[P7/high]** `spec_flow_runner.py:6416–6423` — The HITL rejection branch emits `rework after HITL rejection` but control falls through unconditionally to `self.tasks[nid].status = "done"` and `self._completed += 1`, counting a human-rejected node as successfully completed and contributing a false DONE to the aggregate run verdict.

5. **[P6/high]** `spec_flow_runner.py:7368` — `_nonweb_capability_boots` and `_assembled_product_boots` launch `python3 -c probe` without clearing `PYTHONPATH` or passing `-I`, leaving host `.pth` files and site-packages visible; a package absent in the workspace venv can satisfy the boot gate via a host install, producing a non-hermetic false green. (also at :7406)

6. **[P7/high]** `spec_flow_runner.py:6364` — The binary status mapping promotes any verifier status that is not literally `"FAIL"` (e.g. `"ERROR"`, `"UNKNOWN"`, `"SKIP"`) to PASS, so a verifier signalling an error condition rather than a clean determination contributes a false PASS to the integration conjunction.

7. **[P4/high]** `spec_flow_runner.py:5825` — When multiple parallel children fail concurrently only `errs[0]` is raised; all remaining exceptions are silently discarded with no exit code, cause, or owner attribution, leaving N-1 failures completely invisible in the event ledger.

8. **[P7/high]** `spec_flow_runner.py:5436` — When the lint-rework loop exhausts both rounds without clearing all violations the `if not _lint_spec_traceability(...)` branch is skipped and execution falls through to `_consult_reviewer`; a reviewer PASS then emits `spec_review=PASS` while unresolved `spec_lint=FAIL` events remain, breaking the gate conjunction and letting a lint-dirty spec be marked PASS overall.

9. **[P3/high]** `spec_flow_runner.py:7015` — The guard `if 'Repair directive (integrate acceptance RED)' not in base` prevents the spec from being updated with the current-round failure reason in repair rounds 2+; the implementer is re-invoked against the stale round-1 directive when the failure changes between rounds, leaving the prose carrier permanently out of sync.

10. **[P3/high]** `spec_flow_runner.py:7318` — After each module-targeted repair round `_try_synthesize_entry()` refreshes the structure carrier but `_write_interface_contract()` is never called, leaving `contracts/interface.json` stale relative to the reworked module's surface — the data carrier is omitted from the replacement cycle.
